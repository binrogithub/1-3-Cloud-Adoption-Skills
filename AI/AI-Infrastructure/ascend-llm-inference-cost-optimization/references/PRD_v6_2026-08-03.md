## 0. 一次性配齐的代价，以及为什么本轮可以接受

逐项 A/B 的唯一价值是归因。**本轮不做 A/B 也不会失去归因，因为每一项改动
都有自己在同一轮内可独立观测的指纹信号**——见 §1 表格最后一列。
真正无法归因的只有"多项同时小幅影响吞吐"这种情况，本轮用 §4 的回退阶梯兜底。

明确接受的风险：若 C384 失败，需要一次回退运行（C256 全配置）才能定位，
即最坏情况多花一轮——仍少于逐项 A/B 的 3-4 轮。

## 2. 代码改动（三处，改完即冻结）

### 2.1 `agent90_mix.py:73` — rank 必须按会话 ID 派生

当前用**列表下标**，`hot_ids * R` 会让同一会话在多个 rank 间跳
（r=0 得 `j%8`，r=1 得 `(j+28R')%8`），**亲和静默失效**：

```python
def items(ids, turn):
    return [(make(sid, turn), sid % ndp) for sid in ids]
```
churn 保持 `i % ndp`（它本就是用来制造驱逐的，不需要亲和）。

### 2.2 指标聚合

multi-port 下每个端口只暴露自己引擎的指标。`--metrics-url` 改为接受逗号分隔
的多个 URL（或内部展开 8002-8009），把 8 份文本拼接后再做 delta。
**不改这一项，`prefix_cache_hits` 只反映 1/8 流量，本轮全部缓存证据作废。**

### 2.3 新增 `--hot-unique`，与请求池解耦

`--pool-mult` 会同时放大唯一热会话数（mult=3 → 84，wp1-l1 实测命中率崩到 7.2%）。
新增绝对值参数，**保持 70/20/10 混合比例不变**：

```python
p.add_argument("--hot-unique", type=int, default=0,
               help="唯一热会话数（绝对值）；0=沿用 28*pool_mult。"
                    "复用次数自动推导为 112*pool_mult/hot_unique，混合比例不变")
...
n_hot_req = 112 * mult                     # 70%
hot_unique = args.hot_unique or 28 * mult
hot_reuse  = n_hot_req // hot_unique
hot_ids = list(range(namespace + 1000, namespace + 1000 + hot_unique))
...
measured.extend(items(hot_ids * hot_reuse, 1))
```

## 3. 工作负载参数（维持 10% 冷）

**C384 用 `--pool-mult 4 --hot-unique 56`：**

| 项 | 值 | 说明 |
|---|---:|---|
| 测量请求总数 | **640** | ≈1.67× 并发，足以形成稳态 |
| 热（HBM） | 448 (**70%**) | 56 唯一会话 × 8 次复用 |
| 温（DRAM） | 128 (**20%**) | 128 唯一，一次性 |
| **冷** | 64 (**10%**) | 64 唯一，一次性——**维持不变** |
| churn | 56 | 恒定 |

### 3.1 KV 预算校验（v5 §2 模型）

- C384 在飞占用/引擎 = (384÷8) × 65,280 = **3,133,440**（81.9%）
- 剩余可缓存 = 3,826,957 − 3,133,440 = **693,517**
- 亲和下每引擎只需存 56÷8 = 7 个热会话 × 57,344 = **401,408**
- **余量 1.7×** → 可行

> 对照：无亲和需 56 会话全复制 = 3,211,264 ≫ 693,517，**只装得下 22%**——
> 这就是亲和必须与 C384 同时配齐的原因。

### 3.2 Mooncake 容量校验

温会话 128 × 57,344 × 12.3 KB ≈ **90 GB**，churn 56 × 65,535 × 12.3 KB ≈ **45 GB**，
合计远低于 1100 GB 池容量。**前提是每轮启动前重置**（配置项 3）。

### 3.3 rank 分布校验（数学上应完全均匀）

会话 ID 为连续整数，`sid % 8` 天然均分：
每端口 = 7 热会话×8 复用 + 16 温 + 8 冷 = **80 请求**，8 端口共 640。
实测极差 >20% 即说明 §2.1 未生效。

## 5. 明确排除项（本轮不配，附理由）

| 项 | 排除理由 |
|---|---|
| `gpu-memory-utilization` > 0.918 | C384 在飞 KV 已占 82%，提高利用率会压缩 MoE 临时分配空间，正是历史上 32768 budget OOM 的失败类别。**收益不确定、失败代价是整轮作废。** |
| `max-num-batched-tokens` 改 10240/12288 | 同上，C384 下更大的 prefill chunk 抬高临时分配峰值。留到并发定档后单独验证。 |
| 强制 MoE alltoall | 未验证过的通信路径切换，属于新变量而非"已验证优化"。本轮只核查日志记录实际选择。 |
| W8A8 | 精度门从未做过，成本赢也不能上线。 |
| MTP | 版本门控（vllm#43559 等），修复未落地前禁开。 |
| FlashComm v2 / inter-prefill-budget | 需升版，须独立快照。 |
| 冷请求比例改 5% | 用户决定维持 10%；且 v5 §1 已证明改 5% 会让严格口径恶化 76%。 |

## 6. 判定与回退阶梯

### 6.1 一次性通过的判定

| 门 | 阈值 | 不过的处理 |
|---|---|---|
| 零错误 | 640/640 | 先查残留实例（WP0 教训），再查引擎日志 |
| 驱逐门 | measure 窗内 `evicted_size` 增量 = 0 | 本轮作废，扩池或减 churn 重跑 |
| F1 自证 | `running` 峰值 ≈ 384 (±10%) | F1 回归，查 connector 配置 |
| 亲和生效 | 本地 HBM 命中率 ≥45% | 查每端口请求分布 → §2.1 是否生效 |
| rank 均匀 | 每端口请求数极差 ≤20% | 同上 |
| 指标完整 | 8 个 engine 标签齐全 | §2.2 未生效，证据作废 |
| KV 安全 | `kv_usage_max` ≤ 85% | 超过说明缓存被挤压，回退 6.2 |
| 延迟 | 服务端 p99 ≤ 180s | 超过则 C384 不作为推荐点 |
| 吞吐 | tok/s > 739.8（对照 c256-f1f3） | 触发 6.2 回退定位 |

### 6.2 回退阶梯（仅在 C384 未过时按序执行，每步只退一个变量）

1. **C256 + 全部配置**（退并发）：若此轮吞吐/命中率优于 `c256-f1f3`，
   则证明亲和有效、问题出在 C384 的并发过高 → 最优点定在 C256-C320 之间。
2. **C384 + `--hot-unique 28`**（退热集大小）：每引擎只需 200,704，
   余量从 1.7× 提到 3.5×。若此轮过，说明 56 会话在 C384 下太紧。
3. **C384 + internal LB**（退亲和）：仅在怀疑 multi-port 本身有问题时执行。

### 6.3 通过后

三口径（face / hit10 / strict）齐报，更新基线；可选再探 C448
（v5 §2 表理论上限 444），同样规则。**C512 不要跑**——在飞请求 4.18M >
容量 3.83M，物理上不成立。
