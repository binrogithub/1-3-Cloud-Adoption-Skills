## 0. 摘要：目标其实已经达成——取决于用哪个计费口径

| 计费口径 | 当前实测（C256, 10% 冷） | 对 $0.5 目标 | 对 $0.35 目标 |
|---|---:|---|---|
| 面值（缓存 input 全额计费） | **$0.0611** | ✅ 超额 8× | ✅ |
| **命中按 10% 计费（业界惯例）** | **$0.3156** | ✅ | ✅ **已达成** |
| 严格（命中完全不计费） | $0.5874 | ❌ | ❌ |

**在业界通行的"缓存 input 打折计费"口径下，$0.35 的目标在 C256 上已经达成。**
唯一未达标的是严格口径——而 §1 将证明该口径与缓存优化的方向是**相冲突的**。

**直接回答"改成 5% 冷请求"：会让严格口径恶化 76%，不建议为改善指标而调工作负载。**

## 1. 冷请求比例分析：为什么降到 5% 反而更贵

### 1.1 推算（基于 c256-f1f3 实测常量）

实测关系：`需重算 tokens ≈ 冷请求数 × 65,280`
（c256-f1f3：32 冷 × 65,280 = 2.089M，实测 must-compute 2.10M，误差 0.5%）。

10% → 5% 冷（320 请求中 32 → 16 冷），时长按三档假设推算
（少做的 prefill 按实测 60K tok/s 折算，新增的 DRAM 恢复按 119K tok/s 折算）：

| 场景 | 时长 | output tok/s | $/M output | face I+O | hit10 I+O | **严格 I+O** |
|---|---:|---:|---:|---:|---:|---:|
| 实测 10% 冷 | 110.7s | 739.8 | 15.65 | 0.0611 | **0.3156** | **0.5874** |
| 5% 冷·悲观（时长不变） | 110.7s | 739.8 | 15.65 | 0.0611 | 0.4120 | 1.1379 |
| 5% 冷·中性（净省 9.9s） | 100.9s | 812.3 | 14.25 | 0.0557 | 0.3752 | 1.0363 |
| 5% 冷·乐观（全省 17.6s） | 93.1s | 879.5 | 13.16 | 0.0514 | 0.3465 | 0.9571 |

**方向（中性档）：output $/M 改善 9%，hit10 恶化 19%，严格口径恶化 76%。**
即使最乐观的时长假设，严格口径也只到 $0.957——仍比现在差 63%。

### 1.2 机理：严格口径奖励"缓存未命中"

严格口径 = （未命中的 input）+ output。**缓存命中的 token 完全不计费，
但它们照样占用 DRAM 恢复带宽、HBM 容量和机时——房租一分不少。**

于是：缓存做得越好 → 可计费 token 越少 → 严格 $/M 越高。
降低冷请求比例正是"把可计费的部分变没"，分子掉得比分母快，单价必然上升。

**这是一个方向相反的激励**：按严格口径优化，最优解是关掉缓存。
显然不合理，所以问题不在工作负载，在口径定义。

### 1.3 结论与建议

1. **不要为了改善指标去调工作负载的冷请求比例。** 冷比例应当反映真实生产的
   会话复用率，是一个需要业务侧回答的事实问题，不是可调参数。
2. **建议采用 hit10（缓存 input 按 10% 计费）作为对外口径**：它是业界惯例
   （主流厂商缓存读取价约为标准输入价的 10%），经济上自洽（缓存命中确实消耗
   资源，只是更少），且当前已达成 $0.35。
3. **仍建议实测一轮 5% 冷**——不是为了让数字好看，而是作为**敏感性证据**：
   如果生产复用率确实更高，需要知道各口径怎么变。§4.3 给出实施方法。
4. **待决策（需业务侧）**：对外计费用哪个口径？这决定 $0.35 是"已达成"
   还是"结构上不可达"。**在口径定案前，不应再以严格口径驱动技术方案选型。**

## 2. 每引擎 KV 预算模型：为什么亲和必须排在 C384 之前

实测常量：每引擎 KV = **3,826,957 tokens**（`bf16-16die.log`），
单请求在飞占 ≈ 65,280 tokens，单热会话缓存占 ≈ 57,344 tokens（块对齐）。

> **可用缓存空间/引擎 = 3,826,957 − (C ÷ 8) × 65,280**

（vLLM 的 `kv_cache_usage_perc` 只计在飞引用块；被缓存但未引用的块记在 free
队列里按 LRU 可被驱逐——所以"能留给缓存的"就是总量减去在飞占用。）

**无亲和**（会话可能落到任意引擎 → 热集须在每个引擎复制）：

| 并发 C | 在飞占用/引擎 | 剩余可缓存 | 换算热会话 | 28 会话全复制需求 | 判定 |
|---:|---:|---:|---:|---:|---|
| 256 | 2,088,960 (54.6%) | 1,737,997 | 30.3 | 1,605,632 | 勉强装下（92%） |
| 384 | 3,133,440 (81.9%) | 693,517 | **12.1** | 1,605,632 | ❌ 只装得下 43% |
| 512 | 4,177,920 (109%) | 负数 | 0 | — | ❌ 在飞本身即超容量 |

**模型自校验**：C256 预测 54.6% vs 实测 `kv_usage_max` 53.1% ✓；
wp1-l1（84 唯一热会话，需 4.82M 而仅 1.74M 可用，36% 装得下）实测命中率 7.2% ✓。

**有亲和**（会话固定引擎 → 每引擎只需存 U÷8 = 3.5 会话 = 200,704 tokens）：

| 并发 C | 剩余可缓存 | 亲和需求 | 余量 | 判定 |
|---:|---:|---:|---:|---|
| 256 | 1,737,997 | 200,704 | 8.7× | ✅ |
| **384** | 693,517 | 200,704 | **3.5×** | ✅ 可行 |
| 444 | 202,517 | 200,704 | 1.0× | ⚠️ 理论上限 |
| 512 | 负数 | — | — | ❌ 不可能 |

**结论：亲和把并发天花板从 ~272 抬到 ~444，同时把热层命中率从 31% 拉向 ~100%。
先无亲和跑 C384，缓存会被在飞请求挤掉，结果无效。**

## 3. 必改的四处代码

| # | 位置 | 问题 | 改法 |
|---|---|---|---|
| 1 | `agent90_mix.py:73` | `items()` 用**列表下标**派生 rank（`i % ndp`），`hot_ids*4` 使同一会话在两个 rank 间跳（r=0→`j%8`，r=1→`(j+4)%8`），**亲和静默失效** | `[(make(sid, turn), sid % ndp) for sid in ids]` |
| 2 | `--metrics-url` | multi-port 下每端口只暴露自己引擎的指标，只抓 8002 等于只看 1/8 流量 | 聚合 8002-8009 后汇总 |
| 3 | 请求池参数 | `--pool-mult` 会同时放大唯一热会话数（3→84，wp1-l1 实测命中率崩到 7.2%） | 新增 `--hot-reuse`（默认 4），提并发时加复用次数而非唯一会话数 |
| 4 | 冷请求比例 | 当前硬编码 `cold=16*mult`（10%） | 新增 `--cold-frac`（默认 0.10），供 §4.3 敏感性实测 |

churn 保持 **56 条恒定**（F3 已修，不随 ndp 膨胀），其 rank 仍用 `i % ndp`
——它本就是用来制造驱逐的，不需要亲和。

## 4. 实施

### 4.0 每次启动的前置（WP0/F3 教训，不可省）

```bash
# 1) 杀干净并断言（SO_REUSEPORT 让端口冲突永不以 bind 失败暴露）
pkill -f "vllm serve" || true; sleep 5
n=$(ps -eo args | grep -c "[v]llm serve"); [ "$n" -eq 0 ] || { echo "FATAL 残留 $n"; exit 1; }
# 2) 重置 Mooncake 池；确认 evicted_size=0、allocated 归零、
#    capacity=1,099,511,627,776 (16×64GiB)
# 3) 逐端口 smoke（用 /v1/completions，不是 /health——僵尸实例的 /health 也可能 200）
for p in 8002 8003 8004 8005 8006 8007 8008 8009; do
  curl -s -m 90 http://127.0.0.1:$p/v1/completions -H 'Content-Type: application/json' \
    -d '{"model":"Qwen3.6-35B-A3B","prompt":"hello","max_tokens":4}' | grep -q '"text"' \
    || { echo "FATAL port $p smoke failed"; exit 1; }
done
```

### 4.1 WP-C：会话亲和（P0，先做）

服务端基于 `start-bf16-16die.sh` 新建 `start-bf16-16die-dpm.sh`，**只加两行**：

```bash
  --data-parallel-multi-port-external-lb \
  --data-parallel-supervisor-port 8020 \
```
其余（`ASCEND_RT_VISIBLE_DEVICES=0..15`、`--data-parallel-size 8`、TP2、EP、
budget 8192、seqs 128、0.918、sync、Mooncake connector）一字不动。
8 引擎监听 **8002-8009**；supervisor 用 8020，**不得落在 8002-8009 区间内**
（`dp_supervisor.py:106-112` 会拒绝）。客户端**不要**设 `KV64K_DISABLE_RANK_URL`。

在已验证的 C256 上单变量对比（唯一变量 = 亲和）：

```bash
python3 agent90_mix.py --run-id 70 --concurrency 256 --pool-mult 2 --dp-engines 8 \
  --url http://vllm-host:8002/v1/completions \
  --output .../wpC-c256-affinity.json
```

**判定（对照 `c256-f1f3.json`）：**

| 指标 | 当前 C0 | WP-C 目标 C1 |
|---|---:|---:|
| 本地 HBM 命中请求占比 | 31% | **≥45%**，理想 ≥65% |
| 外部 DRAM 命中占比 | 72% | 显著下降 |
| output tok/s | 739.8 | ≥739.8 |
| hit10 I+O | 0.3156 | < 0.3156 |

命中率不升 → 先查每端口请求数分布（应均匀），再谈其他。

### 4.2 WP-B3：C384（仅在 WP-C 通过后）

```bash
python3 agent90_mix.py --run-id 80 --concurrency 384 --pool-mult 2 --hot-reuse 8 \
  --dp-engines 8 --url http://vllm-host:8002/v1/completions \
  --output .../wpB3-c384-affinity.json
```
唯一热会话仍 56，测量请求 = 56×8 + 64 + 32 = **544**（≈1.4× 并发，够形成稳态）。
> 亲和下 56 会话 ÷ 8 = 7 会话/引擎 × 57,344 = 401,408，C384 剩余 693,517，
> 余量 1.7×——可行但比 28 会话紧。若 WP-C 显示余量吃紧，
> 改用 `--pool-mult 1 --hot-reuse 16`（28 唯一会话）。

**停止规则（写死，避免逐级漂移）：**

| 条件 | 动作 |
|---|---|
| 驱逐门 ≠ PASS（measure 窗内 `master_evicted_size_bytes` 增量 ≠ 0） | 本轮作废，扩池或减 churn 后重跑 |
| 任何错误 | 作废并排查（先查残留实例） |
| 服务端 p99 > 180s | 停止阶梯，C256 为最终点 |
| tok/s 相对 C256 增幅 < 10% | 停止阶梯，并发已到顶 |
| `kv_usage_max` > 85% | 停止，已进入缓存被挤压区 |
| 本地命中率较 WP-C 下降 > 10 个百分点 | 停止，缓存被在飞请求挤掉 |

**C512 不要跑**：在飞请求 4.18M > 容量 3.83M，物理上不成立。

### 4.3 WP-E：冷比例敏感性（P2，与口径决策配套）

用 §3 改动 4 的 `--cold-frac`，在 WP-C 通过后的最优配置上各跑一轮
`--cold-frac 0.10`（对照）与 `--cold-frac 0.05`，**三口径全部报告**。
目的是给口径决策提供实测依据，**不是**用来替换基线。
预期方向已在 §1.1 推算：output 改善、hit10 与严格口径恶化——
若实测方向与推算相反，说明时长模型有误，需重新审视。

## 5. 验收门

继承 v4：驱逐门增量=0、零错误、running 自证（峰值 ≈ 标称并发 ±10%）、
单实例断言、`/v1/completions` smoke、结果文件名与内容一致。

**新增：**
1. **multi-port 指标聚合**：`--metrics-url` 必须汇总 8002-8009，否则
   `prefix_cache_hits` 只反映 1/8 流量，缓存证据无效。
2. **rank 分布均匀性**：每端口请求数极差 ≤ 20%（56 会话÷8=7 应整除，
   不均即为 bug）。
3. **三口径齐报**：任何成本结论必须同时给出 face / hit10 / strict 三个数
   与所用口径，不得只报其中一个。

## 6. 预期与风险

- **WP-C**：命中率 31% → 45-70%，wall-clock 缩短，hit10 $0.3156 → 约 **$0.27-0.29**。
- **C384**：若亲和生效，output tok/s 有望 900-1000，$/M output 降到 **$12 左右**，
  hit10 约 **$0.25**。
- **严格口径**：即便两项全拿满也到不了 $0.35（§1.2 已说明该口径的结构性冲突）。
  **该目标的合理性应随口径决策一并重估，不应继续驱动技术选型。**

| # | 风险 | 处置 |
|---|---|---|
| R1 | multi-port 下 8 个 API server 指标/健康分散 | §5 门 1 强制聚合；smoke 逐端口 |
| R2 | `sid % ndp` 分布不均 → 负载倾斜 | §5 门 2 监控；不均改一致性哈希 |
| R3 | C384 在飞 KV 占 82%，额外内存峰值可能触发 OOM | 逐级跑，先 C384 不跳 C448 |
| R4 | 亲和使单引擎故障影响面集中 | 本轮为性能验证，生产化另议 |
| R5 | 口径未定案导致返工 | §1.3 已把它降级为"不阻塞 WP-C/B3"——两项在任何口径下都是正向改进 |
