## 0. 摘要：查出两个缺陷，WP1 结论与部分历史基线作废

WP1-L1（C256/池512）实测 410 tok/s、$28.20/M，比基线 561 tok/s 更差，
现场结论是"KV 准入上限锁死"。**该结论不成立。** 本轮取证查到两个独立缺陷：

| # | 缺陷 | 性质 | 证据强度 |
|---|---|---|---|
| **F1** | 压测客户端 aiohttp 连接池默认 `limit=100`，**所有标称 >C100 的实验实际都跑在 ~C100** | 仪器缺陷 | 已证实（代码 + 数据双证） |
| **F2** | DP8 无会话亲和，本地 HBM 命中率从 DP4 的 ~55% 崩到 **~12%（≈1/8）**，热流量全落 Mooncake DRAM 慢路径 | 部署/设计缺陷 | 已证实（跨 9 轮命中率对比） |

**"KV 准入上限"是不存在的**：每引擎 KV 容量 3,826,957 tokens = 58 个 64K 会话，
8 引擎 = **467 并发上限**；`max_num_seqs` 128×8 = 1024。实测 running 95、
KV 用量 23.7%、waiting 仅 4——引擎是**饿着**，不是满的。压不上去的是客户端。

## 1. WP0 结案方案（僵尸共听者）

根因已定案：8002 端口上曾同时存在健康 DP8 实例与 W8A8 时代残留的 API server
（引擎已死）。vLLM 用 `SO_REUSEPORT` 绑端口，**第二个实例绑同端口不报错**，
两个监听者按连接四元组哈希分流，故 244×EngineDeadError + 75×Connection reset。
19:39 UTC 全量重启后已消失，`wp0-recompute-c256-320` 与 `wp1-l1` 均 480/480 零错误。

**方案（三层，全部为防复发，必须进脚本而非靠记忆）：**

1. **启动前置断言**（改 `start-*.sh`）：
   ```bash
   pkill -f "vllm serve" || true; sleep 5
   n=$(ps -eo args | grep -c "[v]llm serve")
   [ "$n" -eq 0 ] || { echo "FATAL: $n 个残留 vllm serve，端口会被静默共享"; exit 1; }
   ```
   要点：`SO_REUSEPORT` 决定了端口冲突**永远不会以 bind 失败的形式暴露**，
   不主动断言就永远看不见。
2. **bench 前置 smoke**：必须打 `/v1/completions` 并校验返回 200 + 有 token，
   **不得用 `/health`**（僵尸实例的 `/health` 也可能 200）。
3. **单端口部署必须禁用 rank 改写**：internal-LB 模式下设
   `KV64K_DISABLE_RANK_URL=1`，否则 `rank_url()` 会把请求改写到 `8002+rank`，
   而 8003-8009 无监听者。

`kv_load_failure_policy` 与 Mooncake 配置**无需改动**（已被 `wp0-recompute` 证伪为无关）。

## 2. WP1 调查：F1 客户端连接池上限 100

### 2.1 代码证据

`agent90_mix.py:77` 与 `kv64k_bench.py:174`：
```python
async with aiohttp.ClientSession(timeout=timeout) as session:   # 未传 connector
```
aiohttp 3.13.5 的 `TCPConnector` 默认 **`limit=100`**（`limit_per_host=0`）。
`run_batch` 的 `asyncio.Semaphore(concurrency)` 放行了 256 个协程，
但其中最多 100 个能真正持有 HTTP 连接，其余在连接池里排队。

### 2.2 数据证据：running 完美复现 100 的天花板

| 标称并发 | 实测 running 峰值 | 判定 |
|---:|---:|---|
| C32 | 32 | ✓ 未触顶 |
| C64 | 64 | ✓ 未触顶 |
| C128（8-die） | 94-99 | ✗ **触顶** |
| C128（16-die） | 86-96 | ✗ 触顶 |
| C256（16-die） | 90-95 | ✗ 触顶 |

running 在 C64 前与标称值**逐一相等**，C128 起卡死在 94-99 且**不再随标称并发上升**。
这是连接池上限的教科书特征，与"KV 准入"无关（KV 仅用 23%）。

### 2.3 被此缺陷污染的历史结论（全部作废）

- ❌ 8-die 报告"C128 峰值仅 99 running，故提高并发上限对本工作负载无用"——
  99 是连接池天花板，不是工作负载特性。**"C128 是成本最小点"未被验证过。**
- ❌ PRD v3"16-die 收益要靠更大在飞并发兑现"——该假设从未被真正测试。
- ❌ WP1-L1"池放大反而降吞吐 → KV 准入锁死"——池放大从未提高实际并发。
- ❌ WP1-L1"p99 211s > 180s 硬约束，阶梯停止"——`issue()` 在 `session.post`
  **之前**取 `t0`，故 TTFT 含客户端等连接时间。480 请求 ÷ 100 连接 = 4.8 波 ×
  ~62s ≈ 299s（实测 duration 299.4s，完全吻合）。**该 p99 测的是客户端排队，
  不是服务端延迟，门无效。**
- ❌ WP5 multi-port 会话亲和"因拆并发而失败"——100 条连接分到 4 端口 = 25/端口，
  失败同样源于 F1。**亲和方案未被公正评估过。**

### 2.4 修复

```python
conn = aiohttp.TCPConnector(limit=0, limit_per_host=0, ttl_dns_cache=300)
async with aiohttp.ClientSession(timeout=timeout, connector=conn) as session:
```
（`limit=0` = 无上限；由 `Semaphore(concurrency)` 单点控制并发，语义唯一。）

配套：TTFT 计时点移到 `async with sem:` **之内**，剔除客户端排队；
并在结果里单列 `client_queue_wait_s`，使仪器偏差可见而非隐形。

## 3. WP1 调查：F2 DP8 会话散射摧毁 HBM 层

### 3.1 跨轮次命中率对比（同一工作负载设计：70% HBM / 20% DRAM / 10% 冷）

| 部署 | 唯一热会话 | 本地 HBM 命中率 | 外部(DRAM)命中 tokens | tok/s |
|---|---:|---:|---:|---:|
| 8-die DP4 C32 | 28 | 49.2% | **1.84M**（=设计值） | 324.9 |
| 8-die DP4 C64 | 28 | 45.6% | **1.84M** | 370.3 |
| 8-die DP4 C128 | 28 | 57.0% | **1.84M** | 447.5 |
| 8-die DP4 C128 重复 | 28 | 54.2% | **1.84M** | 467.3 |
| 16-die DP8 (run 10) | 28 | **16.0%** | 6.79M（3.7×） | 532.9 |
| 16-die DP8 (run 11) | 28 | **11.9%** | 6.76M | 561.4 |
| 16-die DP8 (run 13) | 56 | **12.9%** | 13.31M | 549.5 |
| 16-die DP8 (WP0-recompute) | 56 | **11.0%** | 9.78M | 382.3 |
| 16-die DP8 (WP1-L1) | 84 | **7.2%** | 15.96M（8.7×） | 410.4 |

DP4 的外部命中在 4 个轮次里**恒等于 1,835,008 tokens**（=32 请求 × 57,344），
即设计的 20% DRAM 层被精确实现。DP8 的外部命中是设计值的 3.7-8.7 倍——
**本该命中 HBM 的热流量整体漏到了 Mooncake DRAM 慢路径。**

### 3.2 机理

`hot_fill` 让每个热会话在**某一个**引擎上落 KV；`measure` 阶段该会话的 4 次复用
被 internal LB 轮询到 8 个引擎，命中原引擎的概率 = **1/8 = 12.5%**——
与实测 11.9%-16.0% 逐一吻合。DP4 时该概率是 1/4，叠加更少引擎上的自然复制，
实测 45-57%。**引擎数翻倍直接把命中率减半，这是 DP 扩容的内在代价，
不是 16-die 硬件的问题。**

推论：**16-die "只有 +20%" 的真实原因是缓存分层塌了**，不是 EP16 通信开销、
也不是并发不足。$20.62/M 这个"新基线"本身是在退化的缓存状态下测出来的，
与 8-die 的 $24.77 不是同类可比。

### 3.3 修复方向（按优先级，单变量验证）

1. **会话亲和路由**（根治）：`-dpm` multi-port + F1 修复后，每端口可获得真实并发。
   客户端按 `session_id % 8` 定向到 `8002+rank`。F1 修复前该方案无法被公正评估。
2. **备选：缩小唯一热会话数**，使热集在**每个**引擎上都能全量驻留
   （每引擎 3,826,957 tokens ÷ 65,280 = 58 会话；28 会话可全量复制到 8 引擎）。
   这是 DP4 时代生效的隐含机制，但它随引擎数增加而不可扩展，只作过渡。
3. **不要**用"加大请求池"来补偿——已证实反效果（热集变大 → 命中率进一步降到 7.2%）。

## 6. 明确不做 / 禁区

- **不做**：用加大请求池补偿命中率下降（已实测反效果）。

## 8. 追加（2026-08-03 06:40）：F3 — Mooncake DRAM 池被腰斩且已满，测量窗口内持续驱逐

WP-A 修复后跑 C128 得 363.9 tok/s（$31.80/M），低于修复前同标称配置的 532.9。
**该下降与 F1 修复无关**，根因是第三个缺陷。

### 8.1 F1 修复本身已验证成功

| 指标 | 修复前 | 修复后 | 判定 |
|---|---:|---:|---|
| running 峰值（标称 C128） | 86 | **128** | ✅ 自证门通过 |
| waiting_capacity | 4 | 94 | ✅ 真实调度排队首次可见 |
| client_queue_wait | 不可见（混在 TTFT 里） | 87.0s 单列 | ✅ 仪器偏差可见 |

### 8.2 F3 证据：池容量被砍 45%，水位 83-89%，测量中被驱逐

| run | Mooncake 容量 | 水位 | **测量窗内驱逐** | 外部命中率 | 需重算 prompt | tok/s |
|---|---:|---:|---:|---:|---:|---:|
| bf16-16die-c128-160 | 1512 GB | 38% | **0 GB** | 80.1% | 0.42M | 532.9 |
| bf16-16die-c128-320-dp8 | 1512 GB | 76% | **0 GB** | 79.8% | 2.82M | 549.5 |
| wp1-l1-c256-pool512 | **825 GB** | 89% | **+300 GB** | 60.3% | 9.54M | 410.4 |
| wpA-c128-selfproof | **825 GB** | 83% | **+149 GB** | 58.6% | 2.15M | 363.9 |

`master_total_capacity_bytes` 从 1,511,828,488,192（8×176 GiB，旧 8-die 配置）
变为 824,633,720,832（16×48 GiB）——**是 19:39 UTC 那次僵尸清理重启顺带
重新注册了新的 segment 配置**，池容量少了 45%。

wpA 测量窗内 `master_evicted_size_bytes` +149.3 GB、`master_evicted_key_count`
+9,215、`master_key_count` **净减 2,663**——**基准自己刚写进去的 warm 前缀
在测量过程中被 LRU 扔掉了**。修复前两轮该增量恒为 **0**。

### 8.3 因果链

池容量 -45% + `ndp` 4→8 使 churn 从 224 涨到 448 请求（≈352 GB/轮写入）
→ 池水位冲到 83-89% → 测量窗内持续驱逐 warm 层
→ 外部(DRAM)命中率 80% → 58.6%
→ 需重算 prompt tokens 0.42M → 2.15M（**5.1×**）
→ measure 耗时 76.9s → 112.6s
→ 吞吐 532.9 → 363.9 tok/s

**多出来的时间全部花在重算本该命中缓存的 prefill 上。**

### 8.4 三个变量同时变了（违反 v4 §6 单变量原则）

修复前后的对比不成立，因为同时变了三项：
1. Mooncake 容量 1512 → 825 GB（19:39 重启的副作用，无人察觉）
2. churn 请求 224 → 448（`ndp` 4→8，旧脚本默认 ndp=4）
3. F1 修复：有效并发 ~86 → 128（更多并发 KV 写入，加剧池压力）

三者同向加压，其中 (1) 是越过驱逐水位线的决定性一项。

### 8.5 修复方案

1. **P0 每轮测量前重置 Mooncake 池**（重启 master 或 flush）。
   churn 每轮写入 ≈352 GB，825 GB 的池 2 轮就饱和——不重置则**每一轮
   都在测量退化后的缓存状态**，成本数字无意义。
2. **P0 恢复池容量**：host 2010 GB，非 Mooncake 占用 ≈770 GB，
   安全上限 ≈16×64 GiB = 1100 GB（当前 825 GB）。不要回到 16×88 GiB
   （=1512 GB，会撞 host RAM）。
3. **P0 新增验收门**：measure 窗内 `master_evicted_size_bytes` 增量必须为 **0**，
   否则该轮作废——warm 层在测量中被销毁的运行不得用于任何成本结论。
4. **churn 规模改为按引擎恒定**：现在 `56 × ndp` 使 churn 随引擎数线性膨胀，
   与"每引擎驱逐压力恒定"的设计意图不符，且直接撑爆池。

### 8.6 被 F3 污染、需重跑的结论

- ❌ **WP1-L1 "KV 准入上限锁死"**：该轮测量窗内驱逐 300 GB，外部命中仅 60.3%，
  需重算 prompt 高达 9.54M。它测的是缓存塌陷，不是准入上限。
- ❌ **wpA-c128 的 363.9 tok/s / $31.80/M**：同样无效。
- ⚠️ **$20.62/M "16-die 新基线"（run 11）**：池水位当时较低且驱逐为 0，
  数据本身有效，但它是 `ndp=4`（224 churn）测出来的，与后续 `ndp=8` 轮次不可比。

**重跑顺序**：先做 §8.5 的 1-3 项，再重跑 WP-A 自证（C128/C256），
然后才是 WP-B 基线阶梯。在池重置机制到位前，不要再产出任何成本数字。
