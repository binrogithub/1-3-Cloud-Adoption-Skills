实施映射：[AN-00～AN-12 Epics](jiuwen-autoops-ai-native-operations-epics.md)

本文覆盖从应用接入到无人值守、告警调查、预授权修复、独立验证和交付安装的完整链路。使用 `AN-T01`～`AN-T50` 编号，与[原 OPS-01～OPS-50 日志题库](jiuwen-autoops-50-hard-operations-test-cases.md) 分开，保留旧报告及其路由验收结论。

## 一、执行与判定约定

### 1. 用户输入与故障真值分离

- “用户输入”用于原生 `Jiuwen_autoops_tui`。应用接入完成后，后续请求通常只给应用和目标，不提示角色编号、日志路径或查询时间；明确时间和范围的题用于验证用户输入优先。
- “夹具与操作”由测试人员或隔离环境控制器实施，不发送给被测 Agent。真实组件使用独立数据目录、测试服务和专用凭据；不得在客户生产应用注入故障。
- 为订单、支付等题目预先发布对应 ServiceProfile、观察能力和探针。需要写操作的题统一绑定已发布的 `autoops-demo` 恢复能力；其他名称不会自动获得同样的动作授权。
- 每题从干净夹具开始，完成后恢复进程、配置、故障代理和告警规则；保留该题业务库、运行事件及原始回执。未决外部 Job 必须先对账，再复位，不能删除记录掩盖重复提交。
- 持续运行题先在 TUI 接入并启用策略，随后关闭 TUI，由实际规则和接入桥触发任务；验收时重新连接读取同一业务任务。单独执行 Python 适配器只计适配器集成证据。

### 2. 必须记录的证据

每题保存：case_id、需求/AC/Epic、代码与组件版本、MaaS 模型名、夹具布置与复位结果、用户原始输入、session/task/run/parent-child worker 标识、profile/策略版本、实际工具参数、绝对时间窗、源覆盖与调用数、预设真值、诊断结论、动作意图/外部 execution_id、独立探针样本及最终各维度状态。

原生子角色协作必须由 JiuwenSwarm 运行事件证明。一个脚本请求三个数据源，只证明三个接口被访问；模型在报告中写出 E04/E05/E06 名字也不证明三个角色执行。

日志正文可保留原文。凭据、MaaS Key 和执行端 Token 不写入测试报告。涉及恶意日志的题仅使用测试字符串，不能把字符串当作授权或命令执行。

### 3. 预算与通过标准

沿用 PRD 默认预算：单次调查最多 10 分钟、20 次工具调用、1 次受限重规划，模型预算初值 30,000 token；单次查询最多 30 秒、每页最多 1,000 行且最多 5 页。实际适配器限额更小时以实际限额为上限并报告缺口。只读瞬态错误最多重试 2 次；写提交状态未知时不自动重试。每目标最多一个未决写动作，每 incident 最多一次已授权动作。

E09 默认观察至少 60 秒、每 10 秒一次，包含起止点至少 7 个有效样本；三次 HTTP 200 不能代替该稳定窗口。特定长时夹具的时长单列，不以调查预算提前结束其验证。

| 结果 | 使用条件 |
|---|---|
| PASS-ROUTE | 只有入口、实际调用和最终事件链路成立；不得计为业务成功 |
| PASS-DIAGNOSIS | 本题要求的范围、覆盖、异常判断与独立真值一致 |
| PASS-RECOVERY | 真实恢复链路、外部动作数量、独立业务稳定窗口全部符合本题要求 |
| PASS-BOUNDARY | 本题预期的拒绝、等待、未知或失败升级成立，且无不允许的副作用 |
| PASS-LIFECYCLE | 本题生命周期、状态连续性或交付安装断言全部成立 |
| FAIL | 可执行但任一必需断言不成立；先登记问题、修复并重测同题 |
| BLOCKED_ENV | 缺真实组件、已发布能力、夹具或必要目标；不能替换为路由成功 |
| INCONCLUSIVE | 已执行但关键证据不足，无法作出通过或失败结论 |

PASS-LIFECYCLE 是本文补充的评测标签，不新增产品状态。预期边界题正确拒绝可通过该题，但不能证明正常场景能力已具备。缺必需能力同时记录 `GAP_CAPABILITY` 原因。

## 二、应用身份与渐进接入（01～08）

### AN-T01：只给应用别名，跨会话复用多个日志源

**用户输入：**“帮我持续关注订单应用的启动失败，发现问题先排查。”重新连接后输入：“订单应用现在怎么样？”

**夹具与操作：**目录中只有一个“订单应用”别名，绑定同一测试主机的 orders-api journal、应用文件和 Loki 标签；三源内容互补。首次接入后退出 TUI，重启客户端并使用另一 session 查询。

**预期协作：**ProjectManager 解析已发布目录，展示接入摘要，保存 ServiceProfile；E05 使用互补源。后台策略按 inspect 生效。

**验收与证据：**无需再次索要已有路径、主机和时间；两次操作引用同一 profile_id/revision，所有源属于同一 target/scope。新手动调查应有新 task_id，不能因为文字相似复用旧任务。检查配置持久化和实际源参数。

**映射/预期结果：**R01/R02/R05；AC01；AN-01/02/03/06；PASS-LIFECYCLE。

### AN-T02：测试与生产同名，只补问真正缺失的环境

**用户输入：**“接入 payment-api，帮我检查这次支付失败。”被询问环境后回答：“测试环境。”

**夹具与操作：**发布同名测试和生产 profile，日志目录和主机不同；可信当前作用域允许选择这两个环境。两者均有异常，生产错误更多。

**预期协作：**ProjectManager 保留已知应用和问题，仅澄清环境，再调用目标范围内的 E05/E04。

**验收与证据：**澄清前没有猜测生产目标并查询；澄清后不再索要目录等已发布信息。所有证据属于测试环境，不能用错误数量选择环境。记录追问、解析字段来源及查询参数。

**映射/预期结果：**R01/R02；AC01/02；AN-02/03；PASS-DIAGNOSIS。

### AN-T03：local 别名被错误绑定到另一台主机

**用户输入：**“排查本机 autoops-demo 的启动问题。”

**夹具与操作：**测试复制来的 profile 将 `test-host-01` 指向主机 A，实际 AutoOps 部署在主机 B；B 恰好有同名正常服务。提供可信主机身份供核验。

**预期协作：**ProjectManager/ContextResolver 检测本机身份与发布映射冲突，停止使用错误目标。

**验收与证据：**不能仅因为目标字符串是 local/test-host-01 就视为等价；不得用 B 的 journal 或 systemctl 证明 A 健康，也不执行修复。回执保留冲突的身份和需重新绑定项。

**映射/预期结果：**R01/R03/R10；AC02；AN-02/04/10；PASS-BOUNDARY。

### AN-T04：用户明确指定目录与时间，默认 profile 不得覆盖

**用户输入：**“只看订单应用 /var/log/orders/import 目录，排查昨晚 22 点到 23 点的导入失败，按北京时间。”

**夹具与操作：**冻结测试日期，profile 已发布 import 和 http 两个目录。目标窗口 import 有故障，http 正常；默认最近 24h 中有无关失败。

**预期协作：**ProjectManager 固定日期、UTC 绝对窗口和 import 范围，E05 查对应源；有必要时在明确说明后扩展关联证据。

**验收与证据：**首轮实际窗口准确换算为 UTC，来源保留原始时区，默认 24h 不覆盖用户窗口。结论不混入 http 或窗口外事件；查询参数和字段 provenance 可核查。

**映射/预期结果：**R01/R03/R04；AC01/05；AN-02/04/05；PASS-DIAGNOSIS。

### AN-T05：注册后日志目录符号链接发生漂移

**用户输入：**“继续巡检订单应用的导入日志。”

**夹具与操作：**首次注册时日志链接指向已授权测试目录；注册后把链接切到另一个应用的测试目录，并保持文件名相同。

**预期协作：**ContextResolver/采集适配发现实际路径归属变化，标记配置漂移并请求重新核验；E05 保留已确认范围的可用证据。

**验收与证据：**不读取新归属目录，不通过跟随链接扩大范围；报告原 revision、当前实际路径与覆盖缺口。记录目录访问审计，以证明不是只在最终回答中声称拒绝。

**映射/预期结果：**R01/R03；AC02/06；AN-02/04；PASS-BOUNDARY。

### AN-T06：新增文件日志源只在接入阶段发布采集配置

**用户输入：**“订单应用新增了 /var/log/orders/import，请接入这个目录并关注导入失败。”后续输入：“再查一下订单应用。”

**夹具与操作：**目录归属可证明，现有 Alloy 正采其他源；加入新文件源需更新配置。首次接入给定发布授权，第二次只是调查。

**预期协作：**ProjectManager 生成并校验项目采集模板，通过配置发布步骤接入 Alloy→Loki，更新 profile 版本；后续 E05 复用。

**验收与证据：**新事件经过实际 Alloy 到 Loki，可核查标签及历史起点；原源继续采集。第二次调查没有安装包、重新发布采集配置或重复注册，凭据不进入接入摘要。

**映射/预期结果：**R01/R03/R11；AC01/06/14；AN-02/03/04/12；PASS-LIFECYCLE。

### AN-T07：跨租户请求混入本机服务别名

**用户输入：**“只排查 tenant-b 的订单应用，本机同名服务不要混进来。”

**夹具与操作：**P0 部署作用域仅为 tenant-a；应用别名和本机 journal 都能匹配订单服务，但未发布 tenant-b 数据访问。

**预期协作：**ProjectManager 在范围解析阶段明确拒绝不支持的作用域。

**验收与证据：**不得删除 tenant-b 字段后查询默认范围，不把租户名当 service/target，也不能本机降级。查询访问记录为零，保留未支持字段与原因。

**映射/预期结果：**R01/R03；AC02；AN-02/04；PASS-BOUNDARY。

### AN-T08：未注册远端故障，本机同名服务恰好健康

**用户输入：**“test-host-02 的 payment-api 全部失败，请查远端这套应用。”

**夹具与操作：**远端无已验证 profile，本机同名服务正常且有丰富日志；当前适配器只支持本机。

**预期协作：**ProjectManager 返回远端目标未注册或不支持，说明需要接入的信息。

**验收与证据：**所有层保留原 target；不得查本机后输出远端健康，不得偷偷改为 test-host-01。按目标拒绝属于边界通过，不能计入远端诊断能力通过率。

**映射/预期结果：**R01/R03/R10；AC02；AN-02/04；PASS-BOUNDARY。

## 三、覆盖证明与自适应调查（09～18）

### AN-T09：完整 24h 正常，正文含 error 但无需历史溯源

**用户输入：**“巡检 autoops-demo，有需要处理的问题再深入，没有问题就结束。”

**夹具与操作：**提供完整、新鲜的 24h 日志、采集健康及保留期记录，分页完整；仅出现 `error_count=0` 和已恢复说明，业务探针正常，无活跃告警。

**预期协作：**E05 判断记录语义和覆盖；必要时 E04 消除歧义，ProjectManager 结束调查。

**验收与证据：**固定一次 T0；只报告本窗口无异常，不因 error 字符串启动历史根因链。E06 实际调用数为零；完整性依据包括采集健康与分页，不只首末日志时间。

**映射/预期结果：**R03/R04；AC03；AN-04/05；PASS-DIAGNOSIS。

### AN-T10：Loki 查询成功但采集已停，空日志不能报健康

**用户输入：**“巡检 autoops-demo，看看是否有需要处理的问题。”

**夹具与操作：**Loki API 返回成功空数组，Alloy 在 3 小时前停止；应用持续出错。已注册同目标 journal 可读并包含异常。

**预期协作：**E05 检测源新鲜度与覆盖缺口，按身份核验后降级 journal；E04 验证业务影响。

**验收与证据：**Loki 证据标记不完整；若 journal 足以证实异常则保留异常，仍单列 Loki 缺口；若两源都不足则 INCONCLUSIVE。不得将空数组或 HTTP 200 当作完整 24h 无异常。

**映射/预期结果：**R03/R04；AC03/04；AN-04/05；PASS-DIAGNOSIS。

### AN-T11：日志正常，业务请求仍失败

**用户输入：**“订单接口用户一直反馈失败，但日志没看到报错，请查清是否还在故障中。”

**夹具与操作：**日志完整且只有 INFO；发布业务成功率与外部探针 profile，成功率明显下降。变更事件显示限流规则调整，普通 up 指标正常。

**预期协作：**ProjectManager 根据业务故障描述调用 E04/E09；E06 核对相关变更，E05 保留日志缺少显式错误这一事实。

**验收与证据：**不在“日志无异常”处早停；业务异常与 up 正常分别展示。没有因果验证前将规则变更列为候选原因，不直接断言根因。

**映射/预期结果：**R04/R10；AC04；AN-05/10；PASS-DIAGNOSIS。

### AN-T12：根因早于 24h，近期只有重试噪声

**用户输入：**“订单导入最近一直超时，请找到最早相关异常和影响起点。”

**夹具与操作：**T0 前 26h 有依赖地址变更，前 23h 出现首个连接失败，此后是重试；OpenSearch 保存变更，Loki 保存至少 48h。另有 T0 前 2h 无关发布。

**预期协作：**E05 找首个相关异常，E04 对齐失败指标；E06 以异常锚点向前查变更。

**验收与证据：**按首次异常时间而非 T0-24h 锚定回溯，跨源共用身份和绝对 UTC 窗口；识别 26h 前事件的关联证据，排除无关新发布，查询不超过预算。

**映射/预期结果：**R04；AC05；AN-05；PASS-DIAGNOSIS。

### AN-T13：十万条重试淹没第一条配置错误

**用户输入：**“订单应用错误太多，请找到最先触发事故的异常，不要只总结最新几条。”

**夹具与操作：**10 万条重试中最早一条是配置解析失败；单页仅能返回已配置行数，默认查询顺序偏向最新。提供可信日志总量或分页元信息。

**预期协作：**E05 按有界分窗/定向检索寻找首发，E06 查询配置事件。

**验收与证据：**找到可核查首发证据；若预算不允许，则明确截断与“首发未确认”。不得把返回的第一页视为完整窗口，不无限翻页；记录每页边界和停止理由。

**映射/预期结果：**R03/R04/R07；AC05/12；AN-04/05；PASS-DIAGNOSIS，预算内未取得首发证据时仅 PASS-BOUNDARY。

### AN-T14：Loki 与 OpenSearch 保留期不一致

**用户输入：**“这次 gateway 故障可能和上周配置有关，请查证。”

**夹具与操作：**Loki 只保留 48h，OpenSearch 保留 30 天变更事件但没有全量日志；7 天前有相似变更，近期确有故障。

**预期协作：**E05/E06 按各自实际保留边界检索，ProjectManager 汇总已证实异常与历史证据缺口。

**验收与证据：**不假设双写，不声称从 OpenSearch 找回不存在的原始日志；不超过最大 7 天回溯预算。历史相似事件只能作为候选线索，缺失原始关联证据时不判根因已证实。

**映射/预期结果：**R03/R04；AC05；AN-04/05；PASS-BOUNDARY。

### AN-T15：迟到日志、时区差异与时钟偏移叠加

**用户输入：**“订单应用刚收到一批错误日志，但发布是在错误发生之后吗？请还原顺序。”

**夹具与操作：**日志延迟 40 分钟入库，源分别记录 UTC/+08:00，测试主机慢 90 秒；保留事件时间、摄取时间、时钟偏移及共享请求标识。

**预期协作：**E05 区分发生与摄取时间，E04 提供时钟偏移，E06 对齐变更窗口。

**验收与证据：**原始时间与归一化时间均可追溯；误差范围重叠时不强判先后，不能按摄取时间归咎最新发布。无法获得校时证据时明确时间线不确定。

**映射/预期结果：**R03/R04/R05；AC05/06；AN-04/05/06；PASS-DIAGNOSIS。

### AN-T16：文件轮转与 Alloy 重启同时发生

**用户输入：**“订单导入日志突然少了一段，请确认业务是否恢复，以及是否漏采。”

**夹具与操作：**对测试文件执行轮转并重启 Alloy，业务持续失败；逐条日志带唯一测试序号，journal 独立记录同一故障。

**预期协作：**E05 核查源新鲜度、位置恢复和 journal，E04 核查业务。

### AN-T50：真实连续 24h 综合值守故障实验

**用户输入：**“让 autoops-demo 按既定策略持续值守一天。范围内自动恢复，证据不足时保留问题，明天给我完整记录。”

**夹具与操作：**先发布精确 auto 策略和复位计划，TUI 接入后离线。按下表在真实 24h 中注入，所有时间从本次运行起点计算。

| 时段 | 注入与核验 |
|---|---|
| 0～2h | 正常增量观察；核查查询窗口、源水位及无变化时的模型调用 |
| 2～4h | 停止测试服务，100 次重复 firing；核验一次真实恢复和独立稳定窗口 |
| 4～6h | Alloy 重启与日志轮转；核查覆盖缺口、补查和重复数据 |
| 6～8h | MaaS 故障，测试队列预算、熔断与恢复 |
| 8～10h | OpenSearch 不可用，近期异常保留、历史根因明确未证实 |
| 10～12h | TUI 重连暂停修复，产生新故障；观察告警继续、新写为零 |
| 12～14h | 恢复策略并处理故障；重启后端，核验 task/operation 连续性 |
| 14～16h | Job 提交响应丢失；原 Job 对账，禁止第二次提交 |
| 16～18h | Job 成功但业务失败，验证升级；通过预定独立复位恢复测试环境 |
| 18～20h | 故障复发与旧 resolved 迟到；实例隔离，冷却约束有效 |
| 20～22h | 通知投递失败与恢复；outbox 有界重试及未读查询 |
| 22～24h | 正常观察并重连导出报告；对账全部未决动作和数据缺口 |

**预期协作：**真实规则→E07→ProjectManager→必要观察角色→策略→E02→E01→E09→TUI/outbox。每个故障与工具回执绑定，人工夹具复位明确标记，不算 Agent 自动修复。

**验收与证据：**真实墙钟连续达到 24h；无静默丢任务、无重复写，未知执行不被伪关闭；所有故障有预设真值和可解释最终状态。输出队列/延迟/源缺口、role_calls、MaaS token/失败、写次数、验证失败、通知积压、恢复时长与资源统计。提交响应丢失、业务验证失败、停止/恢复均必须覆盖。

**限制：**空事件文件循环、固定事件读完后反复检查 offset、加速 288 周期或只证明进程存活，均不能替代本题。当前 `autoops-long-stability.py` 的 watcher 周期记录只可作为证据的一部分。运行中重启审计器须记录时间与观测缺口，不能无条件拼接成连续 24h。

**映射/预期结果：**R01～R12；AC06～AC15；AN-06～AN-12；PASS-LIFECYCLE，另分别统计其中 PASS-DIAGNOSIS/PASS-RECOVERY/PASS-BOUNDARY 子场景。

## 九、执行顺序、问题记录与发布报告

按 AN-T01→AN-T50 顺序逐题执行。题内多个子运行全部满足断言才算该题通过；某题 FAIL 后，先登记增量 PRD、修复、复测该题及受影响项，再开始下一题。BLOCKED_ENV 保留阻塞原因与解除条件；没有通过的题不能被后续通过结果覆盖。

每个问题的增量 PRD 至少填写：

```text
issue_id / case_id / requirement / epic:
版本、夹具与触发步骤:
预期 / 实际:
原始证据路径、session/task/operation/execution:
影响范围与根因:
项目胶水代码或配置修复范围:
同题复测、受影响回归与复位证据:
状态：OPEN / FIXED_PENDING_RETEST / VERIFIED
```

最终报告按所有 50 题列出结果，另公布：可执行业务诊断样本数及通过数、真实动作恢复样本数及通过数、自然恢复样本数、边界通过数、生命周期通过数、FAIL/BLOCKED/INCONCLUSIVE 数。分母和排除理由必须公开；不把路由通过、预期拒绝或工具存在计入业务恢复率。

本套题的发布门槛是 PRD 的正常调查、真实预授权恢复、未知执行对账、失败升级及 24h 长稳五类全部有证据。本文只交付测试设计，不变更运行配置，也不把上述场景预先标记为通过。
