Fases de la Migración OMS

Object Migration Service · AWS S3 → HuaweiCloud OBS

Proceso Estándar de Migración OMS

El Object Migration Service (OMS) de HuaweiCloud permite migrar objetos desde AWS S3, Azure Blob, Aliyun OSS, Tencent COS, GCP GCS, o fuentes HTTP hacia HuaweiCloud OBS. El workflow de 6 fases cubre desde el descubrimiento hasta la verificación. A continuación se describe cada fase en detalle, con el ejemplo real demo-bucket-17b5e8a2.

1

DISCOVER Ejecutada Automática

Objetivo: Inventariar el bucket origen y el entorno destino antes de crear cualquier recurso.

Qué se hace:

  • Origen (AWS S3): Listar buckets, obtener región del bucket, listar objetos con key/size/storage_class/ETag, contar objetos y tamaño total.
  • Destino (HuaweiCloud OBS): Listar buckets existentes con hcloud obs ls, verificar región del perfil, obtener project ID y domain ID.
  • Recursos OMS: Consultar Terraform MCP (search_providers + get_provider_details) para obtener schemas de oms_migration_task, oms_migration_sync_task, oms_migration_task_group.

Verificaciones:

Que el bucket origen exista y tenga objetos, que el nombre del bucket destino esté disponible (globalmente único), y que los recursos OMS existan en el provider version.

En esta sesión: La IA usó aws s3api list-objects-v2 para descubrir 15 objetos (~75KB c/u, Weekly Reports Week 10-24). Usó hcloud obs ls para verificar que no existían buckets OBS. Consultó Terraform MCP para obtener schemas de los 4 recursos OMS del provider v1.93.0.

2

PREPARE Ejecutada Requiere usuario

Objetivo: Decidir configuración de la migración y verificar que el destino está listo.

Qué se hace:

  • Región destino: Confirmar región de HuaweiCloud para el bucket OBS (default: la-north-2).
  • Nombre bucket destino: Mismo nombre que origen o uno nuevo. Debe ser globalmente único, 3-63 chars, minúsculas.
  • Tipo de tarea: oms_migration_task (one-time) o oms_migration_sync_task (continuous).
  • Gestión de credenciales: Variables TF (-var) o terraform.tfvars (gitignored).
  • Crear bucket destino: Si no existe, incluir huaweicloud_obs_bucket en el config de Terraform.

En esta sesión: La IA formuló 4 preguntas al usuario. Decisiones: la-north-2, mismo nombre (demo-bucket-17b5e8a2), migración única, variables TF via -var. El bucket OBS no existía → se incluyó huaweicloud_obs_bucket en el config.

3

TERRAFORM Ejecutada Automática

Objetivo: Generar los archivos Terraform para crear el bucket OBS y la tarea OMS.

Qué se hace:

  • main.tf: Provider config con AK/SK explícitas, huaweicloud_obs_bucket, huaweicloud_oms_migration_task con source/destination objects, outputs.
  • variables.tf: Variables para regiones, bucket names, y AK/SK (sensitive).
  • terraform.tfvars.example: Plantilla con valores no sensibles rellenados y sensibles como <REEMPLAZAR>.
  • .gitignore: Ignora terraform.tfvars, *.tfstate*, .terraform/.

Configuración clave del OMS task:

El primer terraform plan falló porque el provider no tenía AK/SK explícitas — la IA corrigió el bloque provider añadiendo access_key y secret_key.

4

APPLY Ejecutada Requiere confirmación

Objetivo: Ejecutar terraform apply para crear el bucket OBS y la tarea OMS.

Qué se hace:

  • terraform plan -out=tfplan con las variables sensibles via -var.
  • Revisar el plan: N recursos a crear, cambios en outputs.
  • Confirmación explícita del usuario antes de terraform apply.
  • terraform apply -auto-approve tfplan — crea bucket OBS + tarea OMS.
  • Si hay errores (ej: OMS.0064), corregir y re-aplicar.

En esta sesión: Plan: 2 to add (bucket OBS + OMS task), 0 to change, 0 to destroy. Usuario confirmó. Primer apply: bucket creado OK (7s), pero OMS task falló con OMS.0064 — description "AWS S3 -> Huawei OBS migration" rechazada. La IA corrigió a "AWS S3 to Huawei OBS migration", re-plan, re-apply: OMS task creado en 7s (id 260661304820157, status 2 = migrando).

5

VERIFY Ejecutada Automática

Objetivo: Verificar que la migración completó y todos los objetos están intactos en OBS.

Qué se hace:

  • Refresh state: terraform refresh para obtener status real de la tarea OMS (no usar terraform output solo — lee state estático).
  • Task status: Verificar oms_task_status = 5 (succeeded). Codes: 1=waiting, 2=migrating, 3=paused, 4=failed, 5=succeeded.
  • Conteo de objetos: Comparar aws s3api list-objects-v2 --query KeyCount vs hcloud obs ls (File number).
  • ETags: Comparar ETags entre S3 y OBS — deben ser idénticos para integridad byte-level.
  • Carpeta oms/: Inspeccionar obs://bucket/oms/ — si está vacía, 0 objetos fallidos.

En esta sesión: terraform refresh → status cambió de 2 (stale) a 5 (succeeded). AWS S3: 15 objetos. OBS: 15 objetos + 1 carpeta oms/ (vacía). Los 15 ETags coinciden exactamente entre S3 y OBS — integridad verificada.

La IA Puede Ejecutar la Migración, Pero Necesita Inputs del Usuario

La IA puede descubrir buckets, consultar schemas, generar código Terraform, ejecutar apply, monitorear status, y verificar ETags de forma autónoma. Sin embargo, hay información que solo el usuario puede proporcionar — ya sea por seguridad (credenciales), por conocimiento del negocio (nombres, regiones), o por autorización (confirmación de apply).

Credenciales y Acceso

🔑

AK/SK de HuaweiCloud Requerido

Access Key y Secret Key para autenticar Terraform provider y hcloud CLI. La IA nunca adivina credenciales — siempre lee de archivos especificados o pide al usuario. En esta sesión: credentials.csv.

🗝️

AK/SK de AWS Requerido

Access Key y Secret Key de AWS con permisos s3:ListBucket + s3:GetObject sobre el bucket origen. OMS las usa para leer objetos del source. En esta sesión: awscredentials.csv.

Decisiones de Configuración

📍

Región destino OBS Requerido

En qué región de HuaweiCloud crear el bucket OBS. La IA recomienda la región del perfil hcloud default. En esta sesión: la-north-2.

🪣

Nombre del bucket destino Requerido

Nombre para el bucket OBS (globalmente único, 3-63 chars, minúsculas). Puede ser el mismo del origen o uno nuevo. En esta sesión: demo-bucket-17b5e8a2 (mismo nombre).

📦

Tipo de tarea OMS Requerido

oms_migration_task (one-time, finito) vs oms_migration_sync_task (continuous, replica cambios futuros). La IA recomienda one-time para conjuntos estáticos. En esta sesión: one-time.

🔐

Gestión de credenciales Opcional (la IA recomienda)

Variables TF via -var (no se persisten) o terraform.tfvars (gitignored). La IA recomienda -var para mayor seguridad. En esta sesión: -var.

Confirmaciones

✅

Confirmación antes de apply Requerido

La IA muestra el plan (N recursos a crear) y espera confirmación del usuario antes de terraform apply. Esto crea infraestructura real en HuaweiCloud.

📝

Instrucción de ejecución completa Opcional

El usuario puede dar una sola instrucción: "Si, puedes hacer la migracion" — y la IA ejecuta todas las fases restantes. En esta sesión, esta instrucción disparó init/validate/plan/apply/verify.

Resumen

La IA puede automatizar ~90% del proceso de migración OMS: discovery, generación de Terraform, init/validate/plan, apply, monitoreo, y verificación. El ~10% restante requiere input humano: credenciales de ambos clouds (por seguridad), decisiones de configuración (región, nombre, tipo de tarea), y confirmación de apply (crea infraestructura real). La skill huaweicloud-oms-migration codifica la regla "Never Hardcode Credentials" — la IA siempre usa variables sensitive, nunca commitea secretos.

Nota: Migración Autónoma con un Prompt Completo

La interacción humana descrita arriba (4 preguntas, credenciales, confirmación) fue necesaria porque el prompt inicial del usuario era breve. Sin embargo, si el usuario proporciona un prompt detallado y exhaustivo desde el inicio — incluyendo toda la información del bucket origen (nombre, región, credenciales AWS), las decisiones de configuración (región destino, nombre, tipo de tarea), las credenciales de HuaweiCloud, y la instrucción de ejecutar sin parar — la IA podría ejecutar toda la migración de forma autónoma sin interacción humana subsecuente.

En ese escenario, la IA solo se detendría si encuentra errores graves: bucket name collision, credenciales inválidas, errores de Terraform apply no resolvibles, o task status 4 (failed). En esos casos, la IA pausaría y solicitaría intervención humana.

Esto significa que el nivel de interacción humano-IA es inversamente proporcional a la calidad y completitud del prompt inicial. Un prompt bien estructurado que anticipa todas las decisiones y proporciona todos los datos sensibles puede reducir la interacción a prácticamente cero.

Monitoreo Detallado de la Migración

La tarea OMS pasa por varios estados desde la creación hasta el éxito. La IA monitoreó el status y verificó la integridad de los objetos.

Estados de la Tarea OMS

CódigoSignificadoAcción
1Waiting to migrateTarea creada pero no iniciada. Verificar start_task = true.
2MigratingEn progreso. Esperar y re-check con terraform refresh.
3Migration pausedPausada via action = "stop". Resume con action = "start".
4Migration failedRevisar objetos fallidos en oms/ folder. Ver troubleshooting.
5Migration succeededProceder a verificación de objetos (ETags, conteo).

Importante: terraform output es estático

terraform output lee del archivo de state local, que solo se actualiza durante apply o refresh. Si la tarea OMS cambia de status asíncronamente (ej: de 2 a 5), terraform output seguirá mostrando el valor viejo. Siempre ejecutar terraform refresh antes de leer el status de una tarea OMS.
