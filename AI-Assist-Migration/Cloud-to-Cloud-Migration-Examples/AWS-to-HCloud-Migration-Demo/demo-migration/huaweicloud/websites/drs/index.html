Qué Tuvo Que Considerar

  • Overlap de CIDR: Ambos VPCs (AWS y HuaweiCloud) usaban 10.0.0.0/16, lo que hacía imposible una VPN. La IA detectó esto automáticamente y seleccionó net_type=eip. El usuario debía entender que el tráfico de replicación iría por internet.
  • Parameter alignment: El RDS de HuaweiCloud tiene defaults distintos (transaction_isolation=READ-COMMITTED, innodb_strict_mode=OFF, lower_case_table_names=1). Sin alineación, el precheck FALLARÍA. La IA manejó esto creando un custom param template.
  • lower_case_table_names es ForceNew: En MySQL 8.0, este parámetro no se puede cambiar después de la inicialización. Debe setearse al crear el RDS. Si se equivoca, hay que destruir y recrear el RDS.
  • Source preparation: El RDS de AWS no era públicamente accesible. Habilitar public access + abrir SG 3306 son cambios temporales que se revierten tras el cutover.
  • Binlog hidden requirement: En AWS RDS, binlog_format=ROW no activa binlogging por sí solo. Se necesita backup_retention_period > 0. En este caso ya estaba habilitado (retention=1).
  • Cutover timing: El cutover se hace cuando RPO=0s (source y target en sync). El usuario debía saber que durante el cutover hay que pausar writes en el origen.

Lecciones Clave y Qué Considerar

Estos son los aprendizajes de esta migración que todo usuario debe considerar al usar IA para migrar bases de datos con DRS.

⚖️

Parameter Alignment: El Precheck Puede Fallar

DRS valida que los parámetros del source y target sean compatibles. Parámetros como transaction_isolation, innodb_strict_mode, y lower_case_table_names tienen defaults distintos entre AWS RDS y HuaweiCloud RDS. Sin un custom param template, el precheck FALLARÁ y bloqueará el inicio del job. La IA creó el template drs-migration-mysql80 con los valores correctos antes de crear el RDS.

🔥

El Trap de lower_case_table_names (ForceNew)

En MySQL 8.0, lower_case_table_names no se puede cambiar después de la inicialización. AWS RDS usa 0 (case-sensitive, Linux) y HuaweiCloud RDS usa 1 (case-insensitive) por defecto. En el Terraform provider, es ForceNew — cambiarlo destruye y recrea el RDS. Debe setearse al crear: lower_case_table_names = "0". DRS precheck falla con DB_TBL_NAME_CASE_SENSITIVE_INCONSISTENCY_FOR_UP si no coincide.

🌐

Overlap de CIDR → net_type=eip

Si los VPCs de origen y destino usan el mismo CIDR (ej: ambos 10.0.0.0/16), VPN es imposible por conflicto de routing. La única opción es net_type=eip: el DRS node obtiene un EIP propio y conecta al source por internet. Esto requiere que el source sea públicamente accesible. En esta sesión, ambos VPCs usaban 10.0.0.0/16 → EIP fue la única opción.

📋

Binlog: El Requisito Oculto de AWS RDS

Para FULL_INCR_TRANS (replicación incremental), binlog debe estar ON. En AWS RDS MySQL 8.0, setear binlog_format=ROW en un parameter group NO activa binlogging. Se necesita backup_retention_period > 0 — esto es lo que activa log_bin=ON. Sin backups automatizadas, log_bin queda OFF y la replicación incremental es imposible. En esta sesión, retention ya era 1.

🔍

Precheck: ALARMs vs FAILEDs

El precheck de DRS distingue entre FAILED (bloquea el inicio) y ALARM (warning, no bloquea). En esta sesión hubo 3 ALARMs: dstDbDiskSize (target más grande que source — informativo), sqlModeConsistency (NO_ENGINE_SUBSTITUTION vs vacío — warning), y srcGtidStatusCheck (GTID OFF — DRS usa binlog position). Ninguna bloqueó. Es crucial revisar el precheck completo antes de start.

📊

RPO/RTO: Cuándo Hacer Cutover

El cutover se hace cuando RPO=0s (Recovery Point Objective): significa que source y target están sincronizados, no hay lag. Se verifica con BatchListRposAndRtos. En esta sesión, RPO llegó a 0s rápidamente (DB pequeña, 1.8MB). Para DBs grandes, el full transfer puede tardar horas y el incremental sync necesita tiempo para alcanzar el lag. Nunca hacer cutover con RPO > 0.

🔄

Version Mismatch: Minor vs Major

El source era MySQL 8.0.45 y el target 8.0.43 (la versión más reciente disponible en HuaweiCloud la-north-2). DRS permite diferencias de minor version — el precheck dbVersionMeetRequirement pasó. Para diferencias de major version (ej: 5.7 → 8.0), se necesita validación adicional de compatibilidad de features.

🛡️

Reuso de Security Group para DRS Node

El DRS node necesita conectarse al target RDS en puerto 3306. En lugar de crear una SG dedicada, se reusó demo-sg (la SG del ECS existente). Esto funciona porque la SG del RDS ya permite MySQL desde demo-sg. Simplifica la configuración y reduce el número de recursos. is_target_readonly = true previene writes accidentales durante la migración.

🧹

Cleanup: Revertir Cambios Temporales

Tras el cutover, los cambios temporales en AWS deben revertirse: (1) revocar regla SG tcp 3306 0.0.0.0/0, (2) deshabilitar publicly-accessible en el RDS, (3) force_terminate + delete el DRS job, (4) remover el DRS job del Terraform state. El RDS destino persiste — solo se limpia recursos temporales.
