Arquitectura de la Migración

El bucket S3 de AWS fue descubierto automáticamente, junto con sus 15 objetos (~75 KB c/u). Se creó un bucket OBS nuevo en HuaweiCloud y una tarea OMS de migración única via Terraform, que copió todos los objetos preservando ETags y metadata. Posteriormente, la IA creó una skill reutilizable para futuras migraciones OMS.

Qué Tuvo Que Considerar

  • Bucket name global uniqueness: Los nombres de bucket OBS son globalmente únicos. El usuario eligió reusar el mismo nombre (demo-bucket-17b5e8a2), lo que funcionó porque estaba disponible en la-north-2. Si colisionara, OMS fallaría al crear el bucket.
  • Migración única vs sync continua: Para 15 objetos estáticos, migración única es apropiada. Sync continua (oms_migration_sync_task) sería útil si el bucket S3 sigue recibiendo objetos nuevos y se quiere mantener OBS sincronizado.
  • Credenciales en CSV: El usuario eligió pasar las credenciales via -var en lugar de usar terraform.tfvars. Esto significa que las credenciales no se persisten en disco (no quedan en tfvars ni en state).
  • Costo de OMS: OMS cobra por objeto migrado + tráfico. Con 15 objetos pequeños (~1.1 MB total), el costo es despreciable. Para migraciones de millones de objetos, conviene revisar el pricing.
  • OMS crea carpeta oms/: OMS crea una carpeta oms/ en el bucket destino para registro de objetos fallidos. En esta migración quedó vacía (todos los objetos migraron OK), pero el usuario debe saber que existirá.

Lecciones Clave y Qué Considerar

Estos son los aprendizajes de esta migración que todo usuario debe considerar al usar IA para migrar object storage con OMS.

🔧

El Provider HuaweiCloud No Usa IMDS (a diferencia de AWS)

El provider huaweicloud de Terraform no tiene fallback a ECS Metadata Service como el provider de AWS. Si no se pasan access_key y secret_key explícitamente en el bloque provider, terraform plan falla con dial tcp 169.254.169.254:80: i/o timeout. Siempre pasar AK/SK en el provider block o via HW_ACCESS_KEY/HW_SECRET_KEY env vars.

🚫

OMS.0064: Descripción No Acepta Caracteres Especiales

El campo description del recurso oms_migration_task rechaza caracteres como ->, <-, =>, <>. Usar "AWS S3 to Huawei OBS migration" en lugar de "AWS S3 -> Huawei OBS migration". El error OMS.0064 con error_detail: request parameter [description] invalid. es específico pero no obvio — la IA detectó y corrigió este error durante la sesión.

🔄

terraform refresh Para Status Real, No terraform output

terraform output lee del state local (estático). Si la tarea OMS cambia de status (ej: de 2 migrando a 5 succeeded), terraform output seguirá mostrando el valor viejo. Ejecutar terraform refresh primero para actualizar el state desde la API de OMS, luego terraform output. Status codes: 1=waiting, 2=migrating, 3=paused, 4=failed, 5=succeeded.

🔍

Verificar con ETags, No Solo Conteo

Comparar solo el numero de objetos entre S3 y OBS no es suficiente — los objetos podrían tener el mismo nombre pero contenido distinto. Verificar que los ETags (MD5 checksums para objetos non-multipart) coincidan entre origen y destino. En esta sesión, los 15 ETags eran idénticos, confirmando integridad byte-level. El consistency_check = "size_last_modified" de OMS garantiza esto durante la migración.

📦

type = "prefix" + object = [""] para Bucket Completo

Para migrar todo el bucket, usar type = "prefix" con object = [""] (prefix vacío = todo). Para selección fina, usar type = "object" con una lista de keys específicas. Para migrar desde URLs, type = "url_list". La elección de type determina cómo OMS interpreta el campo object.

♻️

Idempotencia con object_overwrite_mode

object_overwrite_mode = "SIZE_LAST_MODIFIED_COMPARISON_OVERWRITE" hace que OMS no re-migre objetos idénticos si ejecutas el plan de nuevo. Compara size + last_modified del source vs destination y solo sobrescribe si el source es más reciente. Combinado con consistency_check = "size_last_modified", hace la migración idempotente — seguro para re-ejecutar.

📁

OMS Crea una Carpeta oms/ en el Destino

OMS crea automáticamente una carpeta oms/ en el bucket destino para registrar objetos fallados. En esta migración quedó vacía (0 fallos), pero el usuario debe saber que existirá. Al comparar conteos, restar 1 folder del total del destino: File number: 15 + Folder number: 1 (oms/).

⚡

Migración Única vs Sincronización Continua

oms_migration_task (one-time) copia objetos una sola vez — ideal para conjuntos finitos y estáticos. oms_migration_sync_task (continuous) mantiene el destino sincronizado con cambios futuros en el source — ideal para buckets que siguen recibiendo objetos. Para 15 documentos estáticos, one-time fue la elección correcta. Sync sería overkill y añadiría costo continuo.

🛡️

Credenciales: -var vs terraform.tfvars

Pasar credenciales via -var en línea de comandos significa que no se persisten en disco (no hay terraform.tfvars commited). Sin embargo, las credenciales aparecen en el historial de comandos del shell. Para mayor seguridad, usar TF_VAR_aws_ak=... env vars (no aparecen en ps ni historial). El .gitignore cubre terraform.tfvars y *.tfstate* por si se usa esa alternativa.
