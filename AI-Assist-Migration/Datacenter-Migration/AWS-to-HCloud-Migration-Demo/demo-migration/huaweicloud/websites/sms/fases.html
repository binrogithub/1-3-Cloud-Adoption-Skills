Proceso Estándar de Migración

El Server Migration Service (SMS) de HuaweiCloud define un workflow de 7 fases secuenciales para migrar servidores desde cualquier cloud (AWS, Azure, GCP, on-prem) hacia HuaweiCloud ECS. Cada fase tiene objetivos específicos, verificaciones obligatorias, y requisitos de input del usuario. A continuación se describe cada fase en detalle, indicando si fue ejecutada o saltada en esta sesión.

1

DISCOVER Ejecutada Automática

Objetivo: Inventariar completamente el servidor origen y el entorno destino antes de crear cualquier recurso.

Qué se hace:

  • Origen: Identificar instancia, OS + versión, firmware (UEFI/BIOS), vCPU/RAM, layout de discos, red (VPC, subnet, SG, IPs), y SSH key. Decodificar userData para detectar aplicaciones y dependencias.
  • Destino: Listar VPCs, subnets, security groups, availability zones, flavors, e imágenes públicas en la región target de HuaweiCloud.
  • SMS: Verificar si ya hay servidores origen registrados con el SMS Agent (hcloud SMS ListServers).

Verificaciones:

Que el OS del origen sea compatible, que exista un flavor equivalente en el destino, y que no haya solapamiento de CIDR si se planea usar VPN.

En esta sesión: La IA usó AWS MCP para descubrir el EC2 (instancia, imagen, volúmenes, SG, VPC, subnet) y hcloud para descubrir el entorno la-north-2. Decodificó el userData y detectó un stack LAMP + WordPress con dependencia en RDS.

2

AGENT INSTALL Saltada Requiere usuario

Objetivo: Instalar el SMS Agent en el servidor origen para registrarlo con el servicio SMS.

Qué se hace (normalmente):

  • Descargar el installer del SMS Agent en el servidor origen via SSH.
  • Ejecutar el installer interactivo, que requiere 6 prompts: región de SMS, AK/SK de HuaweiCloud, endpoint, y opciones de configuración.
  • Verificar que el servidor origen aparezca en SMS con state: "waiting" y connected: true.
  • Verificar que los 14 pre-migration checks pasen (OS_VERSION, FIRMWARE, BOOT_LOADER, RSYNC, DISK_INFO, PARTITION_STYLE, FILE_SYSTEM, etc.).

Inputs del usuario necesarios (si no está instalado):

  • SSH access al servidor origen: IP, usuario, y key/password para instalar el agent.
  • AK/SK de HuaweiCloud: El agent los necesita para registrarse con el servicio SMS.
  • Región del SMS API: Ej: ap-southeast-3 (no es la misma que la región target).
  • Root o sudo: Privilegios administrativos en el servidor origen.

En esta sesión: El SMS Agent ya estaba instalado. La IA verificó su estado (state: waiting, connected: true) y los 14 checks (todos OK). Esta fase se saltó completamente. Si no hubiera estado instalado, la IA habría necesitado los inputs listados arriba para automatizar la instalación con un script pexpect.

3

NETWORK Ejecutada Requiere usuario

Objetivo: Decidir y preparar cómo el SMS Agent conectará el origen con el destino.

Qué se hace:

  • Decisión de conectividad: ¿Migración via IP pública o VPN? Para cross-cloud (AWS → HuaweiCloud), IP pública es lo más común.
  • Solapamiento CIDR: Verificar que los CIDRs de origen y destino no se solapen si se planea VPN.
  • Crear red target: VPC, subnet, y security groups en la región destino (si no se usan los existentes).
  • EIP para migración: El ECS target necesita un EIP para que el agent conecte (bandwidth_size en el template).

Inputs del usuario necesarios:

  • ¿Usar red existente o crear nueva? Si crear nueva: CIDR del VPC, CIDR del subnet, puertos del SG.
  • ¿IP pública o VPN? Para cross-cloud, IP pública es el default.

En esta sesión: El usuario eligió crear VPC/subnet/SG nuevos (10.0.0.0/16, 10.0.1.0/24, puertos 22/80/443). Se usó IP pública (use_public_ip = true). La IA creó y aplicó el Terraform de red primero, por instrucción del usuario.

4

TERRAFORM Ejecutada Automática

Objetivo: Crear los recursos SMS (template + task) via Terraform.

Qué se hace:

  • SMS Server Template: Define la configuración del ECS target (VPC, subnet, SG, flavor, AZ, tipo de volumen, EIP). SMS usa este template para auto-crear el ECS con firmware compatible.
  • SMS Task: Vincula el servidor origen (vía source_server_id) con el template (vía vm_template_id). Define tipo de migración (MIGRATE_FILE / MIGRATE_BLOCK), OS type, y opciones de inicio.
  • Provider config: Región del provider = región target (ej: la-north-2). SMS API calls usan la región SMS (ej: ap-southeast-3).

Decisión clave:

Usar SMS Server Template (recomendado, maneja firmware automáticamente) vs pre-crear ECS (requiere matching manual de firmware UEFI/BIOS, configuración explícita de discos, y migration_ip).

En esta sesión: La IA generó migration/main.tf con huaweicloud_sms_server_template + huaweicloud_sms_task, referenciando la red creada en la Fase 3 via data sources. MIGRATE_FILE + LINUX + c6.large.4 + SAS. Consultó la versión del provider (v1.93.0) via Terraform MCP.

5

APPLY & MONITOR Ejecutada Automática

Objetivo: Ejecutar terraform apply para iniciar la migración y monitorear hasta completar.

Qué se hace:

  • Apply: terraform init → terraform plan → terraform apply. Esto crea el template y el task, e inicia la migración automáticamente (action = "start").
  • Monitoreo: Polling de hcloud SMS ShowTask cada 30-60s. El task ejecuta 7 subtasks secuenciales:
CREATE_CLOUD_SERVER  → SMS crea el ECS target desde el template
SSL_CONFIG           → Canal seguro entre agent y target
ATTACH_AGENT_IMAGE   → Adjunta imagen del SMS agent al target
FORMAT_DISK_LINUX    → Formatea discos del target
MIGRATE_LINUX_FILE   → Replicación de datos (el más largo)
CONFIGURE_LINUX_FILE → Configura OS migrado (red, fstab, etc.)
DETTACH_AGENT_IMAGE  → Desconecta imagen del agent

Estados a observar:

EstadoSignificado
RUNNINGMigración en progreso
MIGRATE_SUCCESSMigración completada exitosamente
MIGRATE_FAILMigración falló — revisar error_json

En esta sesión: terraform apply creó 2 recursos en 38s. El task 169e94d3-... quedó en estado RUNNING. La IA monitoreó durante ~48 min hasta MIGRATE_SUCCESS. El subtask más largo fue MIGRATE_LINUX_FILE (~30 min, replicación de 8GB a nivel de archivo).

6

VERIFY Ejecutada Automática

Objetivo: Verificar que el ECS migrado funciona correctamente.

Qué se hace:

  • Obtener el ID del ECS target desde la respuesta del SMS task.
  • Verificar estado del ECS (hcloud ECS ShowServer): status, flavor, IPs, VPC.
  • SSH verification: Conectar al ECS migrado usando la SSH key del origen y verificar: hostname, OS version, kernel, discos, block devices, firmware, y aplicaciones.
  • Verificar que los datos de la aplicación están intactos (ej: wp-config.php presente, Apache activo, PHP funcionando).

Inputs del usuario necesarios:

  • SSH key del servidor origen: Para conectarse al ECS migrado (las keys se preservan en la migración).
  • Usuario SSH: Ej: ubuntu para imágenes Ubuntu.

En esta sesión: La IA hizo SSH con private-key.pem al ECS (110.238.85.32). Verificó: Ubuntu 22.04.5 ✓, UEFI ✓, Apache active ✓, WordPress presente ✓, PHP 8.1.2 ✓, EFI partition intacta ✓.

7

CLEANUP Pendiente

Objetivo: Eliminar los recursos temporales de SMS después de migración y verificación exitosa.

Qué se hace:

  • terraform destroy en los directorios de migración y red — elimina el SMS task, template, y recursos de red temporales.
  • Alternativamente: hcloud SMS DeleteTask + hcloud SMS DeleteTemplate via API.
  • El ECS migrado persiste — solo se limpia metadata de SMS.

La IA Puede Ejecutar la Migración, Pero Necesita Inputs del Usuario

La IA puede descubrir entornos, generar código Terraform, ejecutar migraciones, monitorear progreso, y verificar resultados de forma autónoma. Sin embargo, hay información que solo el usuario puede proporcionar — ya sea por seguridad (credenciales), por conocimiento del negocio (decisiones de arquitectura), o por acceso (SSH keys). A continuación se lista todo lo que la IA necesita del usuario, incluyendo lo que habría sido necesario en fases que se saltaron.

Credenciales y Acceso

🔑

AK/SK de HuaweiCloud Requerido

Access Key y Secret Key para autenticar Terraform (HW_ACCESS_KEY / HW_SECRET_KEY) y el hcloud CLI. La IA nunca adivina credenciales — siempre pregunta al usuario.

🔐

SSH Key del servidor origen Requerido

Llave privada SSH para conectarse al servidor origen (instalar agent si es necesario) y al ECS migrado (verificación post-migración). Las keys se preservan durante la migración SMS.

📦

SSH access al servidor origen Requerido si el agent no está instalado

IP, usuario, y key/password del servidor origen. Necesario en la Fase 2 para instalar el SMS Agent. En esta sesión no fue necesario porque el agent ya estaba instalado.

🛠️

Root/sudo en el servidor origen Requerido si el agent no está instalado

Privilegios administrativos para instalar el SMS Agent. En esta sesión no fue necesario — el agent ya estaba instalado y verificado.

🗄️

Credenciales de la base de datos destino Opcional (post-migración)

Si la aplicación migrada depende de una DB, el usuario debe proporcionar las credenciales de la nueva DB (host, user, password) para reconfigurar la aplicación. En esta sesión: RDS HuaweiCloud en 10.0.1.232, user: root.

Decisiones de Arquitectura

📋

Región origen y destino Requerido

En qué cloud y región está el servidor origen, y a qué región de HuaweiCloud se quiere migrar. Ej: AWS us-east-2 → HuaweiCloud la-north-2.

🌐

Estrategia de red del target Requerido

¿Usar VPC/subnet/SG existentes en HuaweiCloud o crear nuevos? Si crear nuevos: CIDR del VPC, CIDR del subnet, puertos del security group. ¿Migración via IP pública o VPN?

🏷️

Nombre del servidor target Requerido

Nombre que tendrá el ECS migrado en HuaweiCloud. Puede ser el mismo del origen o uno nuevo.

🗄️

Estrategia de base de datos Requerido si la app tiene DB

Si la aplicación depende de una DB externa (como WordPress → RDS), el usuario debe decidir: migrar la DB también, hacerla accesible públicamente, configurar VPN, o migrar el servidor primero y reconfigurar después.

⚙️

Tipo de migración y flavor Opcional (la IA recomienda)

MIGRATE_FILE (compatibilidad) vs MIGRATE_BLOCK (velocidad, Windows-only). Flavor del ECS target (la IA recomienda uno equivalente al origen). Tipo de volumen (SAS, SSD, GPSSD).

Confirmaciones e Instrucciones

✅

Confirmación antes de aplicar Requerido

La IA presenta el plan completo (discovery, decisiones, Terraform a generar) y espera confirmación del usuario antes de ejecutar terraform apply. El usuario puede pedir modificaciones (ej: "crear red primero, después migración").

📝

Instrucciones de ejecución Opcional

El usuario puede dar instrucciones específicas sobre el orden de ejecución, qué aplicar primero, o pasos adicionales post-migración (ej: "reconfigurar wp-config.php para apuntar a la RDS de HuaweiCloud").

🔍

Contexto adicional Opcional

El usuario puede proporcionar contexto útil: qué aplicación corre el servidor, si hay dependencias externas, si hay ventanas de mantenimiento, etc. En esta sesión, el usuario incluyó el contenido completo de la skill SMS como contexto inicial.

Resumen

La IA puede automatizar ~90% del proceso de migración: discovery, generación de código, ejecución, monitoreo, y verificación. El ~10% restante requiere input humano: credenciales (por seguridad), decisiones de arquitectura (por conocimiento del negocio), y confirmaciones (por seguridad operacional). La skill huaweicloud-sms-migration codifica la regla "Never Guess Credentials" — la IA siempre pregunta, nunca asume.

Nota: Migración Autónoma con un Prompt Completo

La interacción humana descrita arriba (4 preguntas, credenciales, instrucciones) fue necesaria porque el prompt inicial del usuario era breve: "migrar un EC2 de us-east-2 a la-north-2". Sin embargo, si el usuario proporciona un prompt detallado y exhaustivo desde el inicio — incluyendo toda la arquitectura de origen y destino (IDs, regiones, OS, firmware, red, flavors), las decisiones de migración (estrategia de DB, red target, nombre del servidor, tipo de migración), las credenciales (AK/SK, SSH keys), y el procedimiento completo a seguir — la IA podría ejecutar toda la migración de forma autónoma sin interacción humana subsecuente.

En ese escenario, la IA solo se detendría si encuentra errores graves: incompatibilidades de firmware no resolvibles, errores de información (datos inconsistentes entre lo declarado y lo descubierto), fallos de conectividad, o errores durante terraform apply o la replicación SMS. En esos casos, la IA pausaría y solicitaría intervención humana para resolver el problema antes de continuar.

Esto significa que el nivel de interacción humano-IA es inversamente proporcional a la calidad y completitud del prompt inicial. Un prompt bien estructurado que anticipa todas las decisiones y proporciona todos los datos sensibles puede reducir la interacción a prácticamente cero, dejando a la IA solo el rol de ejecutor y monitor.
