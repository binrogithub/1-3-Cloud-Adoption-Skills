Proceso Estándar de Migración DRS

El Data Replication Service (DRS) de HuaweiCloud define un workflow de 8 fases secuenciales para migrar bases de datos desde cualquier cloud hacia HuaweiCloud RDS. Cada fase tiene objetivos específicos, verificaciones obligatorias, y requisitos de input del usuario. A continuación se describe cada fase en detalle.

1

DISCOVER Ejecutada Automática

Objetivo: Inventariar completamente la base de datos origen y el entorno destino antes de crear cualquier recurso.

Qué se hace:

  • Origen (AWS): Identificar RDS instance, engine + versión, clase, endpoint, publicly_accessible, backup_retention, storage, VPC, SG, route tables, y parameter group. Extraer parámetros críticos: binlog_format, transaction_isolation, innodb_strict_mode, lower_case_table_names, gtid_mode, sql_mode.
  • Destino (HuaweiCloud): Listar VPCs, subnets, SGs, RDS instances existentes, datastores (versiones MySQL), flavors, AZs, ECS existentes, y project ID.
  • DRS: Verificar links compatibles (ListLinks), node types disponibles (ListAvailableNodeTypes), y direcciones de migración soportadas.

Verificaciones:

Que el engine sea compatible (mysql-to-mysql), que existan flavors en el destino, que el task type (FULL_INCR_TRANS) esté soportado, y que haya node types disponibles.

En esta sesión: La IA usó AWS MCP para descubrir el RDS (demo-db, MySQL 8.0.45, db.t3.micro) y su parameter group. Usó hcloud para descubrir que no había RDS instances en la-north-2, obtener flavors, datastores (max 8.0.43), y verificar compatibilidad DRS. Detectó 6 hallazgos críticos incluyendo overlap de CIDR y parameter mismatches.

2

NETWORK Ejecutada Automática

Objetivo: Determinar cómo el DRS node conectará el origen con el destino.

Qué se hace:

  • Verificar solapamiento CIDR: Si los VPCs de origen y destino usan el mismo CIDR, VPN es imposible.
  • Seleccionar net_type: eip (DRS node obtiene EIP propio), vpn (VPN entre VPCs), o vpc (misma VPC).
  • Para eip: El source debe ser públicamente accesible. El DRS node se coloca en el VPC del destino y conecta al source por internet.

En esta sesión: Ambos VPCs usaban 10.0.0.0/16 → overlap detectado → net_type=eip seleccionado automáticamente. El DRS node obtuvo EIP 46.250.162.93 y IP interna 10.0.1.244 en demo-vpc.

3

PARAM ALIGN Ejecutada Automática

Objetivo: Alinear los parámetros del RDS destino con el origen para que el precheck DRS pase.

Qué se hace:

  • Identificar mismatches: Comparar parámetros críticos entre AWS RDS defaults y HuaweiCloud RDS defaults.
  • Crear custom param template: hcloud RDS CreateConfiguration con los valores del origen.
  • lower_case_table_names: Es ForceNew — debe setearse al crear el RDS, no se puede cambiar después.

Parámetros que DIFFEREN entre AWS y HuaweiCloud:

ParámetroAWS DefaultHuaweiCloud DefaultFix
transaction_isolationREPEATABLE-READREAD-COMMITTEDTemplate → REPEATABLE-READ
innodb_strict_modeONOFFTemplate → ON
lower_case_table_names0 (Linux)1ForceNew al crear RDS → 0
explicit_defaults_for_timestampONOFFTemplate → ON (alarm only)

En esta sesión: La IA creó el template drs-migration-mysql80 (id 86051aa9a79346e1bbef11332700df3epr01) con transaction_isolation=REPEATABLE-READ, innodb_strict_mode=ON, explicit_defaults_for_timestamp=ON. El lower_case_table_names=0 se seteó directamente en el recurso Terraform del RDS.

4

SOURCE PREP Ejecutada Requiere usuario

Objetivo: Preparar el RDS origen para que DRS pueda conectar y replicar.

Qué se hace:

  • Public access: aws rds modify-db-instance --publicly-accessible (para net_type=eip).
  • SG rule: Añadir tcp 3306 from 0.0.0.0/0 (o restringir al EIP del DRS node).
  • IGW route: Verificar que el route table del RDS subnet tenga 0.0.0.0/0 → igw.
  • Binlog: Verificar log_bin=ON (requiere backup_retention_period > 0).

Inputs del usuario necesarios:

  • Credenciales DB admin del origen: Usuario y password para que DRS conecte.
  • Autorización para cambios temporales: Public access y SG rule se revierten tras cutover.

En esta sesión: La IA habilitó publicly-accessible en el RDS, añadió regla SG tcp 3306 0.0.0.0/0, y verificó que el IGW route ya existía. Binlog ya estaba ON (backup_retention=1, binlog_format=ROW). Esperó a que el RDS pasara de modifying a available con publicly_accessible=true.

5

TERRAFORM Ejecutada Automática

Objetivo: Crear el RDS destino y el DRS job via Terraform.

Qué se hace:

  • RDS instance: huaweicloud_rds_instance con flavor, VPC, subnet, SG, AZ, lower_case_table_names, param_group_id, y password.
  • DRS job: huaweicloud_drs_job_v5 con job_type=migration, task_type=FULL_INCR_TRANS, net_type=eip, node_type=high, source endpoint (offline), target endpoint (cloud).
  • Provider config: Región target (la-north-2), AK/SK del usuario.

Decisión clave:

El flavor del RDS destino. El origen era db.t3.micro (2vCPU/1GB). En HuaweiCloud el mínimo es 2vCPU/4GB (rds.mysql.n1.large.2). El usuario eligió el flavor más pequeño.

En esta sesión: La IA generó versions.tf, variables.tf, rds.tf, drs.tf, terraform.tfvars. terraform init (provider v1.93.0) → terraform plan (2 to add: RDS + DRS job) → terraform apply. RDS creado en 5m33s (id d96513f1f6d741ec983f2e3a4be0aca3in01), DRS job en 3m23s (id ad099129-7ba8-4e83-849b-8649da6jb101).

6

VALIDATE Ejecutada Automática

Objetivo: Validar que el DRS node puede conectar al source y al target.

Qué se hace:

  • BatchValidateConnections con end_point_type=so (source) — verifica conectividad al AWS RDS.
  • BatchValidateConnections con end_point_type=ta (target) — verifica conectividad al HuaweiCloud RDS.
  • Ambos deben retornar success: true.

En esta sesión: Source validation: success: true ✓. Target validation: success: true ✓. Ambas conexiones validadas en ~36s.

7

PRECHECK Ejecutada Automática

Objetivo: Ejecutar el precheck de DRS para validar compatibilidad antes de iniciar el job.

Qué se hace:

  • BatchCheckJobs con precheck_mode=forStartJob — inicia el precheck.
  • Esperar 30-60s → BatchCheckResults — obtiene resultados.
  • Revisar: FAILED items bloquean el inicio. ALARM items son warnings no-bloqueantes. PASSED items están OK.

Checks críticos:

CheckDescripción
dbIsolationLevelConsistencytransaction_isolation source = target
innodbStrictModeConsistencyinnodb_strict_mode source = target
srcDstTableNameCaseSensitiveChecklower_case_table_names source = target
srcBinlogFormatCheckbinlog_format = ROW
srcDbBinlogIsOfflog_bin = ON
srcDbConnectionConectividad al source
dstDbConnectionConectividad al target

En esta sesión: Precheck 100% passed, 0 FAILED, 3 ALARMs (no bloqueantes): dstDbDiskSize (source 1.8MB → target 17.6GB, informativo), sqlModeConsistency (NO_ENGINE_SUBSTITUTION vs vacío, warning), srcGtidStatusCheck (GTID OFF → DRS usa binlog position, normal). Todos los checks críticos PASSED.

8

START & MONITOR Ejecutada Automática

Objetivo: Iniciar el DRS job y monitorear hasta que esté listo para cutover.

Qué se hace:

  • BatchStartJobs — inicia el job.
  • Full transfer: SHOWJOBING → FULL_TRANSFER_STARTED → FULL_TRANSFER_COMPLETE. Copia completa de struct + data + index.
  • Incremental sync: INCRE_TRANSFER_STARTED. Replicación continua de cambios via binlog.
  • Monitoreo: BatchListProgresses (progreso %) y BatchListRposAndRtos (RPO/RTO delay).
  • Cutover ready cuando: status=INCRE_TRANSFER_STARTED + RPO=0s.

En esta sesión: Job iniciado → STARTJOBING (30s) → FULL_TRANSFER_STARTED → progress 0% → 100% (struct, data, index todos 100%) → FULL_TRANSFER_COMPLETE → INCRE_TRANSFER_STARTED → RPO=0s, RTO=0s. Full transfer completó en ~30s (DB pequeña, 1.8MB).

9

CUTOVER & CLEANUP Ejecutada Automática

Objetivo: Detener la replicación, limpiar recursos temporales, y revertir cambios en AWS.

Qué se hace:

  • BatchDeleteJobs con delete_type=force_terminate — detiene el DRS job.
  • Esperar a RELEASE_RESOURCE_COMPLETE → BatchDeleteJobs con delete_type=delete.
  • terraform state rm huaweicloud_drs_job_v5 — remover del state.
  • Revertir AWS: revocar SG rule, deshabilitar public access.

Post-migración:

TareaAcción
Repoint aplicaciónActualizar DB_HOST a 10.0.1.232 (RDS HuaweiCloud)
Verificar dataConectar al target RDS y verificar tablas/registros
Monitoreo RDSConfigurar backup strategy, alarms CES

En esta sesión: DRS job force_terminate → RELEASE_RESOURCE_COMPLETE → delete → removed from Terraform state. AWS: SG rule revocada, publicly_accessible revertido a false. RDS origen: available, no público. RDS destino persiste en Terraform state.

La IA Puede Ejecutar la Migración, Pero Necesita Inputs del Usuario

La IA puede descubrir entornos, alinear parámetros, generar código Terraform, validar conexiones, ejecutar prechecks, iniciar replicación, monitorear progreso, y hacer cutover de forma autónoma. Sin embargo, hay información que solo el usuario puede proporcionar — ya sea por seguridad (credenciales), por conocimiento del negocio (decisiones de configuración), o por autorización (cambios temporales en el origen).

Credenciales y Acceso

🔑

AK/SK de HuaweiCloud Requerido

Access Key y Secret Key para autenticar Terraform y hcloud CLI. La IA nunca adivina credenciales — siempre pregunta al usuario o lee de archivos especificados.

🗄️

Credenciales DB admin del origen Requerido

Usuario y password del admin de la base de datos origen (AWS RDS). DRS necesita estas credenciales para conectarse y leer los datos. En esta sesión: admin / ChangeMe123!

🔐

Password DB admin del destino Requerido

Password para el root/admin del RDS destino que se crea en HuaweiCloud. La IA puede generar uno fuerte si el usuario no proporciona uno. En esta sesión: HuaweiRDS2026!Migration

Decisiones de Configuración

📋

Región origen y destino Requerido

En qué cloud y región está el RDS origen, y a qué región de HuaweiCloud se quiere migrar. Ej: AWS us-east-2 → HuaweiCloud la-north-2.

⚙️

Flavor del RDS destino Requerido

Tamaño del RDS destino (vCPU/RAM). La IA recomienda uno equivalente al origen, pero el usuario decide. En HuaweiCloud el mínimo es 2vCPU/4GB. En esta sesión: rds.mysql.n1.large.2.

🔄

Tipo de tarea DRS Requerido

FULL_INCR_TRANS (full + incremental, zero-downtime) vs FULL_TRANS (solo full, requiere downtime). La IA recomienda FULL_INCR_TRANS para minimizar downtime.

📦

Alcance de la migración Opcional (la IA recomienda)

Migrar una DB específica o todas las DBs en la instancia. En esta sesión: migrar todas las DBs.

🌐

net_type Automático (según CIDR)

La IA detecta automáticamente el overlap de CIDR y selecciona eip o vpn. Si hay overlap, eip es la única opción.

Confirmaciones e Instrucciones

✅

Confirmación antes de ejecutar Requerido

La IA presenta el plan completo (discovery, hallazgos críticos, decisiones, Terraform a generar) y espera confirmación del usuario antes de ejecutar terraform apply.

🛡️

Autorización para cambios en el origen Requerido

La IA necesita permiso para habilitar public access y abrir SG rules en el RDS origen. Estos son cambios temporales que se revierten tras el cutover.

📝

Instrucción de ejecución completa Opcional

El usuario puede dar una sola instrucción: "desarrolla toda la migración" — y la IA ejecuta todas las fases sin parar. En esta sesión, esta instrucción disparó la ejecución completa.

Resumen

La IA puede automatizar ~90% del proceso de migración DRS: discovery, parameter alignment, generación de Terraform, validación, precheck, inicio, monitoreo, y cutover. El ~10% restante requiere input humano: credenciales DB (por seguridad), decisiones de configuración (flavor, task type, alcance), y autorización para cambios temporales en el origen. La skill huaweicloud-drs-migration codifica la regla "Never Guess Credentials" — la IA siempre pregunta, nunca asume.

Nota: Migración Autónoma con un Prompt Completo

La interacción humana descrita arriba (5 preguntas, credenciales, instrucción de ejecución) fue necesaria porque el prompt inicial del usuario era breve. Sin embargo, si el usuario proporciona un prompt detallado y exhaustivo desde el inicio — incluyendo toda la arquitectura de origen y destino (IDs, regiones, engine, versión, parámetros, red), las decisiones de migración (flavor, task type, alcance, net_type), las credenciales (AK/SK, DB passwords), y el procedimiento completo a seguir — la IA podría ejecutar toda la migración de forma autónoma sin interacción humana subsecuente.

En ese escenario, la IA solo se detendría si encuentra errores graves: incompatibilidades de parámetros no resolvibles, fallos de conectividad, errores de Terraform apply, o precheck FAILEDs. En esos casos, la IA pausaría y solicitaría intervención humana para resolver el problema antes de continuar.

Esto significa que el nivel de interacción humano-IA es inversamente proporcional a la calidad y completitud del prompt inicial. Un prompt bien estructurado que anticipa todas las decisiones y proporciona todos los datos sensibles puede reducir la interacción a prácticamente cero, dejando a la IA solo el rol de ejecutor y monitor.
